## 2. 渲染与亚克力：实测结论（重要）

在本机（Windows 11 26200，NVIDIA 显卡，150% 缩放）逐一实验后的结论：

| 方案 | 结果 |
| :--- | :--- |
| Slint 默认 Skia（wgpu / D3D12 HWND 交换链） | 窗口完全不透明（交换链仅支持 Opaque Alpha） |
| Skia-OpenGL、FemtoVG（WGL） | 整个窗口不可见（疑为 NVIDIA “DXGI 分层呈现”导致） |
| **软件渲染器（softbuffer，预乘 BGRA）** | **半透明正常，当前默认** |
| DWMWA_SYSTEMBACKDROP_TYPE + ExtendFrameIntoClientArea(-1) | 客户区几乎全透明，内容消失 |
| SetWindowCompositionAttribute(ACRYLICBLURBEHIND) | 忽略客户区 Alpha，窗口变为不透明黑块 |
| winit 透明窗口机制 | 用空区域调用 `DwmEnableBlurBehindWindow`，系统 backdrop 不再绘制 |

因此当前默认：软件渲染器 + DWM 圆角 + 深色模式，**透光但无模糊**。两种系统级方案保留为实验开关：`ANYCAST_ACCENT=1`、`ANYCAST_DWMSBT=1`；渲染器可用 `SLINT_BACKEND=winit-skia-opengl` 等覆盖。

> **⚠️ 以上结论已于 2026-09-23 修订，见第 6 节。** 系统级 Acrylic 已改为默认启用，
> 并补上了此前完全缺失的 `WS_THICKFRAME` 准入样式修复。

软件渲染器的已知限制：`drop-shadow` 系列属性不生效（右键菜单、筛选浮层的投影不会绘制）。

### 若需要真实“毛玻璃”效果的候选方案

1. **显示时抓屏 + 自行模糊**：窗口显示前截取其背后的屏幕区域，降采样后做 2~3 次盒式模糊并着色，作为窗口背景图。不依赖 DWM 与显卡驱动，符合设计文档“视觉类似 Haze，不要每帧全窗口 Blur”的要求。代价是每次唤起约 10~30 ms 且背景为静态快照。
2. **DirectComposition 交换链**：需要绕开 Slint 的 wgpu 表面创建流程，工作量大，暂不建议。

## 3. 另一个已修复的启动时序问题

首次 `show_window()` 在 Slint 事件循环启动前执行，此时 winit 窗口尚未创建，`window_handle()` 为 None，导致 DWM 效果与前置聚焦从未应用。现改为 `finish_native_show()` 以单次定时器重试直至拿到 `HWND`。

## 6. 构建故障根因与亚克力修复（2026-09-23）

### 6.1 构建「卡死无输出」的真实原因：rustc 内存耗尽

此前多次出现 `cargo build` 长时间无输出、后台任务一直 running 却拿不到结果。
经排查，根因是 **rustc 因内存耗尽崩溃**，而非锁冲突或工具链损坏。

- 本机 24 逻辑核心 / 32GB 内存，cargo 默认按核心数**并发起 24 个 rustc**；
- Slint 依赖链（skia / icu / windows-sys）单个 rustc 的 LLVM 峰值内存很高，并发打满即耗尽内存；
- 铁证日志：`rustc-LLVM ERROR: out of memory`、`memory allocation of 524288 bytes failed`。

**连带产生的误导性错误**（排查时极易带偏方向）：
崩溃的 rustc 会在 `target/` 留下残缺中间产物，后续编译随即报出数百条与真实原因无关的假错误：

```
only metadata stub found for `rlib` dependency `core`
can't find crate for `std`
cannot find macro `println` in this scope
exit code: 0xc0000409, STATUS_STACK_BUFFER_OVERRUN
```

**结论：见到「std / core 找不到」这类错误，先查 OOM，不要重装工具链。**

**修复措施：**

| 措施 | 说明 |
| :--- | :--- |
| 新增 `.cargo/config.toml` | `[build] jobs = 2`。实测 j=24 必崩、j=8 仍在 hashbrown / windows-sys 处 OOM、**j=2 稳定**。⚠️ **该结论已被 2026-09-24 的修订推翻，jobs 现为 1**，见第 7 节 |
| 删除冗余 `target2/` | 之前用 `CARGO_TARGET_DIR` 绕锁的产物，导致依赖编译两遍且加剧冲突 |
| 清除残留锁文件 | `.cargo-lock` / `.cargo-build-lock` / `.cargo-artifact-lock` |
| 重装 `rustc` + `rust-std` 组件 | 修掉 `STATUS_STACK_BUFFER_OVERRUN` |

**结果：299 个依赖全部编译通过，0 错误，耗时 7m43s。**

> ⚠️ 一个已澄清的误判：`.rlib` 体积小于同名 `.rmeta` **不是损坏**。
> 新版 rustc 采用元数据分离布局（rlib 只存目标代码，完整元数据在 .rmeta），属正常形态。

### 6.2 亚克力背景：三重阻断的修复

设计稿 65.2 指出的三条阻断，此前只有「实验开关」级别的实现，默认路径下等于未生效。

**修复 1：补回 DWM 准入窗口样式（此前完全缺失）**

新增 `theme::ensure_dwm_admissible()`：用 `SetWindowLongW` 为无边框窗口补回
`WS_THICKFRAME | WS_CAPTION | WS_SYSMENU`，再以 `SetWindowPos(SWP_FRAMECHANGED)`
触发 DWM 重算帧架构。**DWM 对不含 `WS_THICKFRAME` 的裸窗口会拒绝注入系统材质**，
这正是此前「API 调用成功但毫无效果」的原因。

**修复 2：系统级 Acrylic 改为默认启用**

原实现只在 `ANYCAST_DWMSBT=1` 时才启用 DWM 背景材质，默认状态下既无 DWM 模糊、
又只有软件渲染器输出的半透明底色 —— 观感是「透光但无模糊」。
现改为默认走 `DWMSBT_TRANSIENTWINDOW` + 客户区帧扩展，并在失败时回退到
`SetWindowCompositionAttribute(ACRYLICBLURBEHIND)` 兜底。

同时新增「系统透明效果开关」探测（读注册表 `EnableTransparency`）：
当系统关闭透明效果时不走 AccentPolicy 兜底，避免退化成不透明黑块。

**诊断开关**（正常使用无需设置）：
`ANYCAST_NO_ACRYLIC=1` 完全禁用系统材质；`ANYCAST_NO_STYLE=1` 跳过样式补全；
`ANYCAST_ACCENT=1` / `ANYCAST_DWMSBT=1` 仅走单层，用于 A/B 对照。

**运行验证日志：**
```
[INFO anycast::gui::theme] DWM 系统级 Acrylic 已启用（DWMSBT_TRANSIENTWINDOW）
```

### 6.4 首次启动置顶预置

新增 `AppCore::seed_default_pins_if_needed()`，在应用扫描完成后执行：

- 按关键词从**已扫描到的真实应用**中挑选，最多 4 个，因此不依赖用户具体装了什么；
  关键词按优先级：`windows terminal` → `terminal` → `powershell` → `command prompt`
  → `git bash` → `visual studio code` → `vscode` → `cursor` → `anycast`；
- 每个关键词取**名称最短**的匹配项，以优先命中规范入口
  （例如「Command Prompt」优先于「Developer Command Prompt for VS 2022」）；
- 由配置项 `pins_seeded` 保证只执行一次，用户日后手动清空置顶不会被重新灌入；
- 若扫描未匹配到任何应用，**不写标记**，留待下次启动重试；
- 已存在置顶（如从旧版本升级）时只补标记，绝不覆盖用户数据。

GUI 侧 `RecentItemsReady` 处理器已一并补上 `refresh_pinned()`，

### 6.5 视觉验证方法与新增工具

在沙箱/非交互环境下验证桌面 GUI 有两个坑，本次一并解决：

1. **应用扫描返回 0 个**：shell 里的 `ProgramData` / `APPDATA` / `PUBLIC` 可能为空，
   导致开始菜单扫描不到任何目录。启动时显式传入真实路径即可：

   ```bash
   APPDATA="C:\\Users\\30130\\AppData\\Roaming" \
   ProgramData="C:\\ProgramData" \
   PUBLIC="C:\\Users\\Public" ./target/debug/anycast.exe
   ```

2. **目标窗口被遮挡或已隐藏**：`screenshot.ps1` 是抓全屏，抓到的是前台窗口。
   新增 `tools/win_shot.ps1`，一次调用完成
   「按标题找窗口 → `SW_RESTORE` → `HWND_TOPMOST` 置前 → 抓该窗口屏幕区域」，
   中途不会因焦点变化导致目标窗口跑掉：

   ```powershell
   & "D:\Anycast\tools\win_shot.ps1" -title "Anycast" -out "D:\Anycast\target\x.png" -scale 1.0
   ```

   想要验证网格视图时，直接改 `%APPDATA%\Anycast\data\config.json` 的
   `view_mode`（`list` / `grid`）再重启即可，无需模拟点击。

## 7. 主窗口退出任务栏 / Alt+Tab（2026-09-24）

### 现象

打开 Anycast 后任务栏多出一个 Anycast 按钮，与「居中的浮动搜索面板」定位不符
（设计文档第 7 节明确要求「不是传统应用窗口」）。

### 根因：窗口样式有两层，此前只处理了其中一层

| 层 | 决定什么 | 项目现状 |
| :--- | :--- | :--- |
| `GWL_STYLE` | 标题栏、边框、能否缩放 | `no-frame: true` → winit 剥掉 `WS_CAPTION` / `WS_THICKFRAME`；随后 `theme::ensure_dwm_admissible` 又**补回** `WS_THICKFRAME` 以换取 DWM 材质准入 |
| `GWL_EXSTYLE` | **任务栏按钮、Alt+Tab 归属** | **全项目从未设置过** |

`WS_EX_TOOLWINDOW`（工具窗口，不进任务栏 / Alt+Tab）与 `WS_EX_APPWINDOW`
（强制出现在任务栏）都在**扩展样式**里，与 `no-frame` 完全无关。
两者都没动 → Windows 按默认规则给这个顶层窗口分配了任务栏按钮，
按钮图标取自 `ui/main.slint:37` 的 `icon: Icons.tray`，观感上像凭空多出一个 App。

补充前提：Slint 1.18 的 `.slint` 语言层**没有** skip-taskbar 类属性
（`i-slint-compiler` 的 `builtin_elements.rs` 里窗口只有 `no-frame` / `always-on-top` /
`icon` / `title` 等），所以这件事只能在 Rust 侧用 Win32 补。
另注：winit 0.30 的 `with_skip_taskbar(true)` 走的是 `ITaskbarList::DeleteTab`，
**只去任务栏、保留 Alt+Tab**，与本次要的效果不同。

### 修复

- `src/gui/theme.rs` 新增 `hide_from_taskbar(hwnd)`：置 `WS_EX_TOOLWINDOW`、清 `WS_EX_APPWINDOW`。
  ⚠️ 任务栏只在窗口**可见性变化**时重新评估，单纯改样式按钮不会当场消失，
  因此函数内补一次 `ShowWindow(SW_HIDE)` → `ShowWindow(SW_SHOWNOACTIVATE)`；
  用 `NOACTIVATE` 避免抢焦点（前置聚焦仍由 `launcher::force_foreground` 单独负责）。
- `src/gui/mod.rs` 新增 `Gui::fix_taskbar()`，在 `finish_native_show()` 拿到 HWND 时调用
  —— 该处已有「拿不到 HWND 就重试」的时序处理，直接复用。
  ⚠️ **必须每次显示都调用**，不能加「只做一次」的守卫：一次 `hide()` → `show()` 之后
  winit 会把窗口属性重置回默认值，任务栏按钮就复活了。详见 §10。

### 代价（预期内，已与用户确认）

窗口不再出现在 **Alt+Tab**。唤醒方式只剩托盘图标与全局唤醒热键（默认 `Alt+Space`）。
若将来要「只去任务栏、保留 Alt+Tab」，改用 `ITaskbarList::DeleteTab` 即可，不动扩展样式。

诊断开关：`ANYCAST_KEEP_TASKBAR=1` 保持原样，用于 A/B 对照。

### 验证工具

### ⚠️ 编译环境：真凶是「提交限制」，不是并发数

本次 `cargo build` 连续失败于 `rustc-LLVM ERROR: out of memory`。
**根因修正**：`.cargo/config.toml` 里「并发数 × 单 rustc 峰值」的旧结论只是表象，
真正的约束是 Windows 的**提交量（commit）余量**：

| 指标 | 数值 |
| :--- | :--- |
| 物理内存 | 31.74 GB 总 / **9.9 GB 可用**（看着宽裕） |
| 提交上限 | 39.74 GB |
| 已提交 | 37.0 GB |
| **剩余提交余量** | **仅 2.4 GB** ← 撞的是这堵墙 |
| 历史峰值 | 39.74 GB（正好等于上限） |

- 提交上限 = 物理 31.74 + 页面文件 8。注册表 `PagingFiles` 里配了
  `D:\pagefile.sys 49152 49152`，但**该文件不存在**（D 盘还有 144GB 空闲），
  而 `ExistingPageFiles` 把它列了出来——**该值会骗人**。本该有 ~87GB 上限。
- 依赖已全部编好、只剩 bin crate 时，`jobs` 不再起作用（瓶颈是单 rustc 的 ~2GB 峰值）。
  **有效手段是 `-j 1`**：`jobs=2` 时 rustc 从 jobserver 拿 2 个令牌、最多 2 个 LLVM
  上下文同时驻留，`-j 1` 压到 1 个。实测 `jobs=2` + `debug=0` + `opt-level=0` 仍 OOM，
  补上 `-j 1` 才通过（2m02s）。
- 各手段实测：`opt-level=0` 有效（2.19→1.87GB）；`debug=0` **基本无效**（2.15→2.19GB）；
  `CARGO_INCREMENTAL=0` 略有帮助且不牵连依赖。
- OOM 崩在 codegen 途中会写坏 `target/debug/incremental`，链接期随即报
  `LNK2019 无法解析的外部符号` × N + `LNK1120` —— **全是假错误**，
  只删该目录（1.0GB）即可，不必全量重编。

新增 `tools/build_mem_probe.py`：跑一次编译并每秒采样 rustc 提交量与系统余量，
最后打印峰值，用来判断"要腾出多少提交量"。
（写此类探针**必须把子进程输出重定向到文件**，用 `subprocess.PIPE` 后等进程结束再读会因
cargo 输出超 64KB 管道缓冲区而死锁——实测卡死 16 分钟，且症状酷似"残留锁阻塞"。）

### 顺带发现 → 已裁决移除（2026-09-24）

`minimize_to_tray` 是**死开关**：`src/core/settings.rs:93` 有字段、设置面板有开关、
`src/gui/mod.rs:1017` 写回配置，但**没有任何窗口逻辑读它**。

深挖后确认它比「没人读」更彻底 —— **它背后的功能根本不存在**：

- 窗口是 `no-frame: true`，没有系统标题栏最小化按钮；`.slint` 里搜 `minimize`

- 而任务栏按钮已在第 7 节移除，所以「关掉开关 → 不隐藏到托盘」这条路会把窗口
  彻底弄丢 —— 托盘是现在唯一常驻的锚点

**裁决（爽世）：移除开关。** 已删除 `settings.rs` 的字段、`mod.rs` 的

点托盘图标或按唤醒热键唤出」。

用的是逐字段 `#[serde(default)]` 且未开启 `deny_unknown_fields`，无需迁移。

### 构建配置：`[build] jobs` 由 2 固化为 1

`.cargo/config.toml` 里原本是 `jobs = 2`，但第 7 节已实测证明
**`jobs=2` + `debug=0` + `opt-level=0` 照样 OOM** —— 也就是说裸敲 `cargo build` 仍是个陷阱，
只有记得手敲 `-j 1` 才安全。既然裁决是长期走 `-j 1`，就让它成为默认：

```toml
[build]
jobs = 1
```

**等效性验证**（此前怀疑 `[build] jobs` 与命令行 `-j 1` 因 jobserver 令牌机制而"不完全等价"，
本次实测排除）：

```

CARGO_INCREMENTAL=0 cargo build        # ⚠️ 刻意不带 -j
→ Finished in 2m49s，EXIT=0，13 条 warning，无 OOM
```

**结论：两者在本项目等效**，日常直接 `cargo build` 即可。
`D:\pagefile.sys` 修好后可把 `jobs` 改回 2~6 提速（实测 24 必崩、8 仍会 OOM）。

## 8. 修复：从脚本启动时应用扫描静默返回 0 个（2026-09-24）

### 现象

验证任务栏改动时，程序日志出现 `应用扫描完成：0 个`（文档记录为 136 个），
而文件索引正常（`48097 条`）。差点被误判成扫描逻辑坏了。

### 根因：环境变量「存在但为空串」

`src/core/apps.rs` 的 `scan_dirs()` 原实现：

```rust
if let Ok(pd) = std::env::var("ProgramData") {
    dirs.push(PathBuf::from(pd).join("Microsoft\\Windows\\Start Menu\\Programs"));
}
```

**`std::env::var` 对已设置但为空的变量返回 `Ok("")`，不是 `Err`。** 不判空就会拼出
`Microsoft\Windows\Start Menu\Programs` 这个**相对路径**，而 `scan_apps()` 里
`if !dir.exists() { continue; }` 直接跳过 —— 静默返回 0 个。

从 shell / 脚本 / 计划任务 / 工具链启动时，`APPDATA=`、`ProgramData=`、`PUBLIC=`
经常是空串。对照实验：

| 启动环境 | 应用扫描结果 |
| :--- | :--- |
| 三个变量为空串 | **0 个** |
| 补齐三个变量 | **136 个** |

### 修复

`src/core/apps.rs`：

1. 新增 `known_folder(&FOLDERID_*)`：用 `SHGetKnownFolderPath` 取系统已知文件夹，
   **不依赖环境变量**（`CoTaskMemFree` 已配对释放）。
2. 新增 `env_dir()`：`std::env::var(...).ok().filter(|s| !s.is_empty())`，过滤空串。
3. `scan_dirs()` 改为**已知文件夹优先、环境变量兜底**，覆盖
   公共开始菜单 / 用户开始菜单 / 用户桌面 / 公共桌面四处。
4. 目录列表为空时 `log::warn!`，把静默失败变成可诊断。

### 验证

| 启动环境 | 修复前 | 修复后 |
| :--- | :---: | :---: |
| 三个变量为空串 | 0 个 | **134 个** |

（134 vs 旧实现读环境变量时的 136，差 2 个，未深究——两个数都属正常范围。）

### 备注

这类「从脚本启动 → 环境变量为空串 → 静默失败」的坑是通用的，已沉淀为
skill `windows-launch-env-gotchas`（含无头读窗口样式做验证的做法，
避免被 `hide_on_blur` 干扰截图）。

## 9. 修复：候选截断会整档吃掉高分文件（2026-09-25）

### 现象

搜索命中数较多的关键词时，**一批本该排在最前面的文件整档消失**。

真机复现（本机 4.8 万文件，查询 `anim`）：总命中 223 条，其中**以 `anim` 开头**的
有 40 个 —— 这 40 个是 `name_score` 里 85 分的「前缀匹配」档，本该占据前 40 名，
实际**一个都进不了前 50**（实测 0/40）。

### 根因：SQL 的排序键与 Rust 的打分不是一回事

链路是两段排序：

1. `storage::search_files` 取候选：`ORDER BY length(f.name) ASC, f.mtime DESC LIMIT ?`
2. `search::search_files` 重排：`name_score()` 打分 → 稳定排序 → 取前 50

`name_score` 的前三档是**常数分**（精确 100 / 前缀 85 / 词首 70），只有第四档
（包含）是 `55 − 长度×0.2`。而 SQL 那边**只有长度**这一个键 —— 等于拿「名字短」
当「相关度高」的代理。

于是第四档里大量名字很短的「包含」匹配，会把第一/二档里名字较长的文件整体挤出
`LIMIT` 之外。Rust 侧再准也没用：**它看不到这些文件**。

注意第二段排序是 `slice::sort_by`（**稳定排序**），同分元素保持 SQL 给的顺序 ——
所以只要候选集正确，最终顺序就是对的，问题**只在候选集**。

### 修复

**① SQL 加档位排序键（核心）**

```sql
ORDER BY CASE
    WHEN lower(f.name) = ?               THEN 0   -- 精确
    WHEN lower(f.name) LIKE ? ESCAPE '\' THEN 1   -- 前缀
    ELSE 2 END ASC,
  length(f.name) ASC, f.mtime DESC LIMIT ?
```

精确/前缀匹配无条件排在最前，截断只可能落在「其余」档内部 —— 而那一档的分数随
名字长度单调递减，与 `length ASC` 方向一致，所以截断是安全的。

**② 候选上限 100 → 3000**（`search::FILE_CANDIDATE_CAP`）

档位键覆盖不到「词首档（70 分）」—— 在 SQL 里表达「按分隔符切词后某段以 q 开头」
要枚举分隔符，太脆弱。改用「候选取得足够多」来覆盖。本机实测除 `png`(1.5 万命中) /
`jpg`(1 万) 这类极端查询外，命中数都远低于 3000。

**③ 先排序、后构造 item**

候选从 100 涨到 3000 的前提是**不能**对全部候选构造 `SearchItemModel`
（`file_to_item` 要 clone path / name / subtitle）。改为先用纯函数算分排序，
只给选中的前 50 条构造。

**④ 使用统计批量化（顺带修掉一个性能坑）**

`boost_by_usage` 原先对**每个候选项**打 2 条 SQL（`recent_stats` + `is_pinned`）——
100 候选就是 200 条 SQL，涨到 3000 会直接拖垮每次击键。改为 `Storage::usage_stats()`
一次读全（`recent` 表本身有 200 行上限、`pins` 更小）。`idle_items` 里逐条查
`is_pinned` 的 60 次 SQL 也一并收掉。

### 验证

**① 回归测试（含变异测试）**

新增 `core::search::tests::prefix_match_survives_candidate_truncation`：造 120 个
短名字的「包含」匹配 + 1 个长名字的「前缀」匹配，断言后者排第一。

把代码**临时改回旧行为**重跑，该测试如期变红 —— 证明它不是摆设：

```
test core::search::tests::prefix_match_survives_candidate_truncation ... FAILED
前缀匹配的长名字被候选截断吃掉了（这正是旧实现的缺陷）；实际返回 50 条
```

另新增 `usage_bonus_matches_applied_bonus`，守住「排序用的分」与「写回的分」两份
公式不漂移（这类不一致不会有任何编译期或运行期报错）。

全量 `cargo test`：**90 passed / 0 failed**（原 88 + 新增 2）。

**② 真库验证**（4.8 万文件，Python 直接跑同一条 SQL）

| 查询 | 总命中 | 前缀档 | 旧：进前 50 | 新：进前 50 |
| :--- | ---: | ---: | ---: | ---: |
| `anim` | 223 | 40 | **0** | **40** |
| `chat` | 293 | 14 | 13 | 13 |
| `2026` | 893 | 16 | 3 | 3 |

**③ GUI 端到端**：输入 `anim`，列表顶部即 `anime4k_shaders` + `Anime4K_*.glsl` 系列
（85 分前缀档），滚到底部是 `shootAnim` 系列（`shootanim` 整串一个词，落 53 分包含档）
—— 排序梯度完整，整档 40 个文件全部可见。

**④ 诚实的边界：触发条件比想象中窄**

- 任取 55 个「命中 100~1500 条」的查询，修复前后**前 50 条完全一致（55/55）** ——
  因为前缀档本身超过 50 个时，它们本来就排不进前 50，截断与否不影响可见结果。
- 在 32 个「前缀档 ≤ 50 个」的查询里，**只有 1 个（`anim`）**发生实质变化。

所以这是**低频但一旦触发后果严重**的缺陷：不是少显示一两条，而是**整档高分文件消失**。
另外叠加使用加成后（`boost_by_usage` 最多 +45 分），一个用户常用但名字较长的文件
会被截断挡在门外 —— 这条路径在当前 `recent` 只有 1 行的库上还测不出来。

### 成本

档位键要对每一行求值 `lower(f.name) LIKE 'q%'`，最重的查询有感知
（Python 口径的 SQL 取数耗时；Rust 侧更快，且取数只是整个搜索耗时的一部分）：

| 查询 | 命中 | 旧 | 新 | 差 |
| :--- | ---: | ---: | ---: | ---: |

| `jpg` | 10040 | 6.4ms | 12.8ms | +6.4ms |

轻查询基本无变化；极端查询 +10ms 相比 400ms 防抖可忽略。

### 未做

- **词首档（70 分）没有专门的 SQL 表达**，仍靠 3000 的候选上限兜底。要彻底解决得在
  SQL 里表达「按分隔符切词」，收益不抵复杂度。
- **同档内没有区分度**：85 分档里 100 个文件之间只按长度排。用户想找的若恰好是其中
  较长的一个，仍要靠使用加成或补全更多字符。这是 `name_score` 分档粒度的固有局限，
  不在本次修复范围。

## 10. 修复：一次 hide/show 之后窗口样式被 winit 重置（2026-09-25）

### 现象

§7 的「退出任务栏 / Alt+Tab」与 §6.8.1 的「DWM 准入样式」都**只在首次显示时校正一次**
（`Gui::fix_taskbar` 开头是 `if state.taskbar_fixed { return; }`）。
于是 —— **用户按一次唤醒热键（或关窗到托盘再唤出）之后，两处修复同时失效**：

- 任务栏重新冒出 Anycast 按钮
- 右上角重新出现 `—` `□` `×`，`×` 压在筛选漏斗上（设计稿 65.2 的「漏斗套叉」脏图）

两次修复各自都「验过」，但都只验了**首次显示**那一帧，于是谁也没发现它们在第二次显示时
就已经不生效了。

### 根因：winit 在 `hide()` 时把窗口属性重置回默认值

不是系统慢慢改回去，而是**在隐藏那一刻同步发生**的。

### 复现证据（旧二进制，实测）

探针 `tools/win_style_probe.py`：读两层样式位，**同时读 `IsWindowVisible`**
（样式位正确而窗口隐藏 = 假阳性，所以两者必须一起看）。

热键临时改为 `Ctrl+Shift+Space` —— `Alt+Space` 家族合成按键打不进去（见 §「唤醒热键」
一节的排除结论），要验等价行为必须换组合键。

| 时刻 | `visible` | `GWL_STYLE` | `GWL_EXSTYLE` |
| :--- | :--- | :--- | :--- |
| 首次显示 | True | `0x16070000` ✓ | `0x00000198` ✓ |
| 发键一次（→ 隐藏） | False | `0x06CF0000` ✗ | `0x00040118` ✗ |
| 再发一次（→ 唤出） | True | `0x16CF0000` ✗ | `0x00040118` ✗ |

- `WS_CAPTION`(0x00C00000) / `WS_SYSMENU`(0x00080000) 回来了 → DWM 会画标题栏按钮
- `WS_EX_TOOLWINDOW`(0x80) 掉了、`WS_EX_APPWINDOW`(0x40000) 置上了 → 任务栏按钮复活
- **第三次读数证明旧代码补不回来**：`taskbar_fixed` 已为 `true`，`fix_taskbar` 直接早退

截图 `_probe_style_broken.png`：右上角 `— □ ×` 清晰可见，`×` 与漏斗图标重叠。

### 修复

- `theme.rs`：从 `hide_from_taskbar` 拆出 `enforce_taskbar_exclusion` ——
  只写扩展样式位、**不做 hide/show**（无闪烁），幂等早退
- `mod.rs::fix_taskbar`：**去掉「整个函数只做一次」的守卫**，每次显示都跑；
  原 `taskbar_fixed` 降级为「是否首次」的判据，只用来选任务栏那条路径的版本
  （首次走 `hide_from_taskbar`，带 `SW_HIDE + SW_SHOWNOACTIVATE` 逼任务栏重新评估，
  代价是一次可见闪烁；此后走无闪烁版）
- `ensure_dwm_admissible` 本来就幂等（`new_style == style` 早退），每次调用无成本

> **教训**：`if 已修复 { return; }` 这类「只做一次」的守卫，在 winit 下是**错的**——
> winit 会在可见性变化时重新应用窗口属性。凡是对 HWND 属性做的手工校正，
> 都必须假设它随时可能被重置。

### 验证（修复后，同一探针、同一路径）

编译后重启应用，重复上面的读数：

| 时刻 | `visible` | `GWL_STYLE` | `GWL_EXSTYLE` |
| :--- | :--- | :--- | :--- |
| ①首次显示 | True | `0x16070000` ✓ | `0x00000198` ✓ |
| ②发键一次（→ 隐藏） | False | `0x06CF0000` ✗ | `0x00040118` ✗ |
| ③再发一次（→ 唤出） | True | **`0x16070000` ✓** | **`0x00000198` ✓** |

- ② 的偏离是**预期内**：`hide_window()` 不走校正路径，窗口反正不可见，样式坏不坏无所谓
- ③ 才是判据：**唤出后样式被补回来了**。修复前同一时刻是 `0x16CF0000` / `0x00040118`
  （`WS_CAPTION|WS_SYSMENU` 在位、`WS_EX_APPWINDOW` 在位），补不回来
- 连按 2 轮（累计 3 次 hide/show）全部符合期望 → **可重复**
- 截图 `_probe_style_fixed.png`：右上角只剩筛选漏斗图标，`— □ ×` 已消失
  （对照 `_probe_style_broken.png`）

## 11. 修复：设置页里「说了不做」的四个控件（2026-09-25）

起因是核对「清理缓存」按钮，结果发现设置页里有一整类问题：**控件存在、配置写进去了、
但没有任何消费方**。UI 在骗人，而这类缺陷不会有任何编译或运行期报错。

### 逐项核对结果（全量扫过设置页所有可点控件）

扫描方法：把 `settings_modal.slint` 里所有 `Settings.action(...)` / `set-bool` /
`set-string` 的键，与 Rust 侧 `set_setting_bool` / `set_setting_string` 的 match 分支、
以及每个配置字段在 `src/core/` 里的**读取点**逐一对照。判据是「有没有消费方」，
不是「有没有写进 config」。

| 控件 | 位置 | 修前行为 | 根因 |
| :--- | :--- | :--- | :--- |
| 清理缓存 | 常规 · 系统托盘与维护 | 弹「已清理运行时缓存」，磁盘零变化 | 只写了个 kv 键 |
| 双击条目立即执行 | 常规 · 界面与交互偏好 | 关掉后双击依然直接打开 | `double_click_launch` 无消费方 |
| 银行卡与身份证脱敏展示 | 剪贴板 · 隐私与敏感数据保护 | 开关拨动后列表毫无变化 | `clipboard_mask_sensitive` 无消费方 |
| 按需动态唤醒加载 | AI · 本地模型与向量检索 | 拨了没反应 | `ai_lazy_load` 无消费方（本地模型后端尚未接入） |

其余 24 个设置项（自启动、失焦隐藏、主题、亚克力、索引三件套、剪贴板 5 项、AI 6 项…）
核对后**都有真实消费方**，未做改动。

### 各自的修法

**① 清理缓存 → 改成真回收，并报出实际数字**

`Storage::clear_runtime_cache()`：`PRAGMA wal_checkpoint(TRUNCATE)` + `PRAGMA optimize`，
返回 `-wal` 文件的**实际减少量**。与「整理索引库」的区别是**不做 VACUUM**
（VACUUM 要重写整库、占 2 倍磁盘、期间独占写锁，不适合随手点的按钮）。

- 无可回收时如实说「运行时缓存已是干净的，无需清理」，不再每次都报「已清理」
- ⚠️ **本机没有任何缩略图 / 临时文件缓存目录**：`%APPDATA%\Anycast\data\` 下只有
  `anycast.db` + `-wal` + `-shm` + `config.json`，`%TEMP%\Anycast` 不存在
  （它只是 `data_dir()` 的兜底分支）。原型里「已清空本地运行时缩略图与临时缓存
  (释放 14.8 MB)」是**虚构文案** —— WAL 就是唯一的运行时缓存

**② 双击条目立即执行 → 真正接管双击**

`ResultPane` / `PinnedShelf` 各加一个 `in property <bool> dbl-launch: true`，
`main.slint` 里绑 `dbl-launch: Settings.double-click`；
两处 `double-clicked` 改成 `if (root.dbl-launch) { root.activate(...) }`。
关掉后双击退化为「只选中」，`Enter` 不受影响（它走的是另一条回调）。

**③ 银行卡与身份证脱敏展示 → 真做脱敏**

`gui::mask_sensitive()`：识别**银行卡**（连续 15~19 位数字，允许夹单空格 / 短横）
与**身份证**（17 位数字 + 校验位 `X`），保留首 4 位与末 4 位，中段换 `*`，
分隔符与校验位原样保留。

- 只作用于**展示**（`title` / `preview`）——`full_path` 始终是原文，
  而复制 / 打开走的都是 `full_path`，所以用户实际拿到的东西不会被打码
- ⚠️ **必须有分隔符数量上限**（`MAX_SEP = 4`）：否则 `1 2 3 … 12` 这种凑巧 15 位数字的
  普通文本会被整段打码。这条有专门的回归用例守着
- 用 `Cow` 而不是 `clone`：不开脱敏时保持零拷贝
- 顺带补了「改完立刻重绘」——脱敏是纯展示层开关，不重绘的话列表纹丝不动，
  用户会以为开关没生效（和 §7 里那几条是同一类坑）

**④ 按需动态唤醒加载 → 置灰 + 说清**

判断层只有规则引擎（`rule`）与云端（`jev`），本地模型后端（Laya）尚未接入，
所以「懒加载」是**恒真**状态，这个开关没有任何可切换的行为。
与其留一个拨了没反应的开关，不如 `enabled: false` + 说明「本地模型后端接入后生效」。
接入后把 `enabled: false` 去掉、`toggled` 接回 `set-bool("ai_lazy_load", v)` 即可。

## 12. 外部程序用低级键盘钩子抢走 Alt+Space，且 Anycast 检测不到（2026-09-25）

### 起因

用户按 `Alt+Space`，期待唤出 Anycast，结果弹出一个暗色「插件」面板：
占位文字「输入插件名称、拼音或拼音首字母」、空状态「暂无可直接打开面板的插件。」、
右上角 `Alt + Space` 快捷键徽标、底栏「↑↓ 选择　回车打开　Esc 关闭」。
他以为是「又写了个新的启动窗口，把快捷键绑错内容了」。

**不是我们的东西。** 那是 **PI-Desktop**（`%LOCALAPPDATA%\Programs\PI-Desktop`，
文件版本 `0.15.2.0`）的**「插件启动器」**。

### 证据链（三层，互相独立）

**① 文案逐字命中** —— `resources/app.asar` 的 i18n 表里就有这几句：

```js
pluginLauncher: {
  title: "打开插件",
  placeholder: "输入插件名称、拼音或拼音首字母",   // 截图占位文字
  empty: "暂无可直接打开面板的插件。",            // 截图空状态
  noResults: "没有匹配的插件",
  openHint: "回车打开", navigateHint: "↑↓ 选择", dismissHint: "Esc 关闭"  // 截图底栏
}
{ id: "openPluginLauncher", group: "navigation", defaultBinding: "Alt+Space" }
```

全盘扫描 `%LOCALAPPDATA%\Programs` + `D://DeskBox` + `D://Pebrel`（4736 个文件，
UTF-8 与 UTF-16LE 双编码）后，**只有这一个文件**命中这三句特有文案。

**② 窗口归属** —— 枚举顶层窗口按**所属进程**归属：

```
PI-Desktop.exe  pid=34744  hwnd=0x3C0D7A  visible=False
  class='Chrome_WidgetWin_1'  rect=(544,314, 620, 440)  exstyle=0x200008
```

`0x200008` = `WS_EX_TOPMOST | WS_EX_NOREDIRECTIONBITMAP`（无边框置顶浮层）。
而 **620 × 1.5 = 930、440 × 1.5 = 660** —— 正是那张截图的像素尺寸（150% 缩放），
尺寸对得上，不是「看着像」。

**③ 空状态可解释** —— `plugins/installed/` 与 `plugins/disabled/` 都是空的，
`registry.json` 里只有两个内置插件 `pi.browser` / `pi.file-manager`，
`capabilities` 都是 `views`，**没有「可直接打开面板」的插件** → 必然走 `empty` 文案。

### 机制：它为什么绕开了 RegisterHotKey

`crates/host-core/src/keyboard.rs` 的模块注释写得很明白（引用官方仓库源码）：

> Electron's `globalShortcut` uses `RegisterHotKey` on Windows. The shell reserves
> Alt+Space for the active window system menu, so that API can reject the launcher's
> default binding. The low-level hook below is kept deliberately narrow:
> **it only consumes Alt+Space** while enabled and emits an ordinary host notification.

```rust
// 命中 Alt+Space 时：
// Prevent Windows from opening the active window's system menu.
// Electron will show the launcher in response to the host notification instead.
return 1;   // ← 吞键，不调 CallNextHookEx

/// Enable the native hook only for the Windows-reserved default binding.
pub fn uses_windows_fallback(binding: &str) -> bool {
    cfg!(windows) && binding == "Alt+Space"
}
```

也就是说：**PI-Desktop 不用 `RegisterHotKey`，而是 `SetWindowsHookExW(WH_KEYBOARD_LL)`
装了一个低级键盘钩子**（`pi-desktop-host-core.exe` 里有 `SetWindowsHookEx`，
**没有** `RegisterHotKey`）。钩子命中时 `return 1`，键在**投递之前**就被吃掉。

### 要害：这是 Anycast 检测不到的冲突类型

Anycast 判断「唤醒热键能不能用」的办法是 `RegisterHotKey` + 看
`ERROR_HOTKEY_ALREADY_REGISTERED(1409)`。而钩子**不占用注册表**，
所以这条判据完全失明：

| | 常规冲突（对方也用 RegisterHotKey） | 钩子型冲突（对方用 WH_KEYBOARD_LL） |
| :--- | :--- | :--- |
| 我方 `RegisterHotKey` | 失败，`err=1409` | **成功，`err=0`** |
| 我方 `WM_HOTKEY` | 不来 | **不来** |
| Anycast 的 Toast | 弹「注册失败」 | **什么都不弹** |

→ 表现为「设置里显示注册好了，按下去毫无反应」，属于**静默失效**。

### 实测（真机，可逆）

`tools/hotkey_swallow_probe.py`（本轮新增）。同一个消息泵、同一个进程，
**必须**带判据对照，否则「收不到 WM_HOTKEY」还有第二种解释（探针自己坏了）：

```
判据对照（必须收到 WM_HOTKEY，否则本探针结论作废）
  ctrl+alt+shift+f13 注册=True err=0    WM_HOTKEY=True     ← 泵是好的
目标组合键
  alt+space          注册=True err=0    WM_HOTKEY=False    ← 键被吞了
```

同时观测到 PI-Desktop 的启动器窗口 `IsWindowVisible` 从 `False` → `True`，
再按一次 `Alt+Space` 又变回 `False`（它自己的 toggle 语义）。
→ **Alt+Space 确实被 PI-Desktop 吃掉了，可复现。**

### 处置建议

1. **本机**：把 Anycast 默认唤醒键从 `Alt+Space` 换掉（`Alt+`` / `Ctrl+Space` 之类），
   或者在 PI-Desktop 的「设置 → 快捷键 → 插件启动器」里禁用/改绑。
2. **代码**：只看 1409 的可用性检测对钩子型冲突无效。真要检测，得**注册后自检**
   （注册成功再注入一次看 `WM_HOTKEY` 到不到）——注意 `Alt+Space` 恰恰是
   「注入必被吞」的组合键，这个「吞」本身就是可用的检测信号。
   最低限度也应把「注册成功但按键无反应」与「注册失败」在 UI 上区分开，
   别让用户以为绑定生效了。

> ⚠️ **需要复核的旧结论**：`a875d44` 那次「用户物理按键确认 `Alt+Space` 可用」，
> 与本次实测（PI-Desktop 的 host-core 在跑时 `Alt+Space` 到不了 Anycast）**相互矛盾**。
> 合理解释是当时 PI-Desktop 的 host-core 没在跑（它曾长期因
> `DbSchemaTooNewError` 启动失败），钩子没装上。**这条结论要重新确认一次**，
> 不要在 PI-Desktop 运行时把 Alt+Space 当作已验证可用。

### 顺带修正：`Alt+Space` 注入不动的归因

skill `windows-global-hotkey-verification` 里把「`Alt+Space` 注入不动」归因为
**系统菜单加速键**。本机实测的真因是**第三方低级键盘钩子吞键**。
两者会产生同样的消息级现象（`Space` 的 `WM_KEYDOWN` 凭空消失），但后果不同：
系统菜单不会让 `RegisterHotKey` 静默失效，钩子会。以后遇到这类现象，
先跑一遍 `hotkey_swallow_probe.py` 区分，别默认归到系统菜单上。

## 12.1 修复：把「注册成功但按不到」变成看得见的结论（2026-09-25）

### 要解决的问题

§12 的结论是「检测不出来」。但真正该修的不是检测手段，而是**结论的表达**：

| 实际情况 | 旧行为 | 用户看到 |
|---|---|---|
| 键空闲 | 注册成功 | 无提示（正常） |
| 键被 `RegisterHotKey` 占了 | 注册失败 1409 | ⚠ Toast（正常） |
| **键被 LL 钩子吞了** | **注册成功** | **什么都没说 → 以为能用** |

第三行才是要害：它和第一行在**所有可观测信号上完全一致**（`err=0`、无 Toast）。
所以修法是：**在用户主动改唤醒快捷键之后，真注入一次按键，看 `WM_HOTKEY` 到不到**。

### 设计：两相自检 + 三态结论

新增 `WakeDelivery { Delivered, Swallowed, Inconclusive, NotRegistered }`
（`src/core/win_thread.rs`），由 `SystemBus::verify_wake_delivery()` 驱动：

1. **对照相**：注册 `Ctrl+Alt+Shift+F13`（`VERIFY_CONTROL_ID`），注入它，等 `WM_HOTKEY`
   - 没等到 → `Inconclusive`（**这台机器此刻测不了**，不赖键）
2. **目标相**：对照通过才注入当前唤醒键，等 `WM_HOTKEY`
   - 等到 → `Delivered`；超时（`VERIFY_WAIT_MS = 500`）→ `Swallowed`

三条硬约束：

- **对照键必须是「没有程序会响应」的组合**（`F13` + 三修饰键），否则自检本身有副作用。
  测试 `control_combo_is_never_a_real_binding` 守着这一点。
- **`Inconclusive` 这一档不能省。** 少了它，就会把「测不了」误报成「被占用」——
  这正是项目里反复犯过的「环境不行 vs 被测不行」错误。测试
  `only_swallowed_may_blame_the_key` 断言只有 `Swallowed` 的文案允许说「占用」。
- **自检期间收到的 `WM_HOTKEY` 不能当用户按键派发。** 否则点一下「检测」，
  目标相注入的唤醒键会顺手把窗口显示/隐藏一次，看起来像 bug。`wndproc` 里
  先让自检认领（`VerifyStep`），认领到就 `return LRESULT(0)`，不再走 `WakeHotkey`。

### 为什么必须给一个独立的「检测」入口

被钩子吞掉的组合键，**界面根本录不到它**（老实验已证：外部程序占住组合键时，
主键不会送到本进程）。所以「点键帽重新录制」这条路对 `Alt+Space` 走不通 ——
必须在 `全局唤醒快捷键` 那一行旁边放一个不依赖按键送达的
`ActionButton { label: "检测" }` → `Settings.action("verify-wake")`。

### 副作用与文案

自检会**真的注入一次按键**。若该键被别的程序占用，**对方会真的响应**（本机实测：
PI-Desktop 的插件启动器真的弹了出来）。这是唯一能区分两种情况的代价，不能省，
但必须在 UI 上说明 —— 点击时先提示
「正在检测…（若被别的程序占用，它可能会弹出自己的面板）」。

`WakeDelivery::describe()` 写成**独立成句**，两个入口共用一份文案
（文案分叉迟早不一致）：录完键时说「已保存…：」，主动检测时说「⚠ 唤醒快捷键 X：」。

### 验证（真机，2026-09-25）

`cargo test` **99 passed / 0 failed**（新增 3 个测试）。`cargo build` 通过后真机跑：

| 唤醒键 | 结论 | 实测 Toast |
|---|---|---|
| `Alt+Space`（PI-Desktop 在跑） | `Swallowed` | `⚠ 唤醒快捷键 Alt+Space: 按键收不到 —— 有程序用低级键盘钩子占用了它。这种占用不占注册表，所以注册会成功、也不会报冲突，请换一个组合键` |
| `Ctrl+Alt+W`（空闲） | `Delivered` | `✓ 唤醒快捷键 Ctrl+Alt+W：按键投递正常` |

两项同时验证到：

- `Alt+Space` 那次，**PI-Desktop 的插件启动器真的弹出来了**（`IsWindowVisible` 由假变真），
  这是「键被第三方钩子吃掉」的直接物证，不是推断；
- `Ctrl+Alt+W` 那次，**窗口没有显示/隐藏**（截图里设置页原样停着）→
  「自检认领 `WM_HOTKEY`」的抑制生效。

> 实验可逆性：实验前备份了 `config.json`；期间只临时改过 `hide_on_blur`（为了能抓图）
> 和 `wake_hotkey`（换成空闲键做正对照），**结束后逐字段比对备份，差异为零**。

### 仍未做

`verify_wake_delivery` 只对**唤醒键**有效，不覆盖「快捷直达」的绑定 ——
那些可能是 `Ctrl+S` 之类有真实语义的组合，注入它们会往别的程序里打字。
这个限制写在 `AppCore::verify_wake_delivery` 的文档注释里。

## 12.2 归因坐实：把嫌疑进程挂起，键立刻就能到（2026-09-25）

§12 的证据链是「注入 → 收不到 + PI 启动器弹出」，属于**相关性**。
这一节把因果也钉死：**只改一个变量**，其余全不动。

### 方法

`NtSuspendProcess` / `NtResumeProcess`（`ntdll`）把 `pi-desktop-host-core.exe`
整体挂起，再跑同一支探针。脚本 `D:/tmp/hook_owner_ab.py`，
`try/finally` 保证无论如何都会恢复。

> 为什么不用 Toolhelp32 枚举线程再逐个 `SuspendThread`：
> 本机 Python ctypes 下 `Thread32First` 返回 `TRUE` 但结构体读出来是 0
> （`tid=0`），逐线程的路走不通。`NtSuspendProcess` 一次挂起全部线程，也不需要
> `OPEN_THREAD` 权限 —— 只要 `PROCESS_SUSPEND_RESUME(0x0800)`。

### 结果（`Alt+Space`）

| 阶段 | 注册 | `WM_HOTKEY` |
| :--- | :--- | :--- |
| 基线（host-core 在跑） | True `err=0` | **False** |
| `NtSuspendProcess` | True `err=0` | **True** |
| `NtResumeProcess` | True `err=0` | **False** |

挂起它，键立刻能到；恢复它，键立刻又不到。**这不再是「相关」，是「就是它」。**
收尾核对：进程 pid 未变、仍在跑。

### 顺带查清：被吞的不是「`Alt+Space`」这一个键，是整个 `Alt + Space` 家族

对 `Alt+Shift+Space` 跑同一支 A/B，结果一模一样（挂起→能到，恢复→不到）。

对照 `crates/host-core/src/keyboard.rs` 的回调条件，原因很清楚：

```rust
let is_space = key.vkCode == VK_SPACE;
...
if ENABLED.load(..)
    && is_space
    && is_key_down
    && key.flags & LLKHF_ALTDOWN != 0   // ← 只要求「Alt 按着」
    && !SPACE_DOWN.swap(true, ..)
```

**它只检查「`VK_SPACE` + `LLKHF_ALTDOWN` 置位」，不检查其它修饰键。**
所以 `Alt+Shift+Space`、`Alt+Ctrl+Space` 一样会被吃掉。

这条同时修正了 skill `windows-global-hotkey-verification` 里的旧说法 ——
那里把「`Alt+Space` 家族注入不动」归因为**系统菜单加速键**，
真因是**第三方钩子按 `Alt` 位匹配**。两者消息级现象一样，但后果不同：
系统菜单不会让 `RegisterHotKey` 静默失效，钩子会。

### 处置：把本机唤醒键换成实测可用的组合

`Alt+Space` 与 `Alt+Shift+Space` 都被占，`Ctrl+Alt+Space` 则是
`err=1409`（已被别人用 `RegisterHotKey` 占住）。实测可用的：

```
Ctrl+Alt+Q    注册=True err=0  WM_HOTKEY=True   ← 采用
```

改完之后真机验证（`D:/tmp/wake_toggle_test.py`，只读 `IsWindowVisible`，
**不**调用 `ForceForeground` —— 否则探针自己会把窗口 ShowWindow 出来污染判据）：

```
按之前 visible = True
SendInput ctrl+alt+q -> True    按一次后 visible = False
SendInput ctrl+alt+q -> True    再按一次后 visible = True
```

> 当时只改了本机 `config.json`，**代码默认值先没动**（一台机器的冲突不足以动产品默认值）。
> 旧值备份 `D:/tmp/config.before_wakekey_swap.json`。**随后 §12.3 把默认值也改了** ——
> 理由是它不是「这台机器被占了」，而是这个键在产品层面就注定冲突。

### 附记：PI-Desktop 在本轮中途退出了（如实记录，不做归因）

做 §12.4 的复现时发现 `pi-desktop-host-core.exe` 已经不在进程列表里，
启动器窗口句柄也 `IsWindow == False`，而 `Alt+Space` **实测恢复可用**
（`D:/tmp/wake_press_diag.py`：按下后 t=0.10s 窗口就可见且在前台）。

* 没有 Crashpad dump，没有 WER 记录，相关目录最新文件 mtime 停在 `09-25 21:07`。
* 本轮对它做过的唯一操作是上面那次 `NtSuspendProcess` / `NtResumeProcess`，
  带 `try/finally`，且收尾核对过 pid 未变。
* **不归因**：没有证据说明退出与那次挂起有关，也没有证据说明无关。

记在这里是因为：上面那组 A/B 的结论依赖「它在跑」，后来的人复现时会发现它不在，
需要知道这是**中途发生的**，不是一开始就没有 —— 否则会误以为 A/B 的记录对不上。

**顺带印证了 §18.4 的条件性**（见 `doc/检索增强与判断模型接入开发文档.md`）：
PI 退出后 `Alt+Space` 立刻恢复可用，反过来证明那条 🔴 更正是对的 ——
当年「物理按键确认可用」的结论**只在宿主程序没跑时成立**。
键本身一直是好的，变的是**环境**。

## 12.3 默认唤醒键从 `Alt+Space` 改为 `Ctrl+Alt+Q`（2026-09-25）

### 为什么连默认值一起换

§12.2 一开始把这件事当成「本机冲突」，所以只改了本机配置。但把「`Alt+Space` 为什么会被抢」
摊开看，它不是偶发：

1. Windows 把 `Alt+Space` 留给窗口**系统菜单**；
2. 几乎每个启动器类应用（uTools / PowerToys Run / Wox / Listary / PI-Desktop…）
   都拿它当默认呼出键。抢不到 `RegisterHotKey` 的会改用
   `SetWindowsHookEx(WH_KEYBOARD_LL)` **硬吞** —— 而钩子型冲突**不占注册表**，
   `RegisterHotKey` 照样成功、`err=0`，只有真按一次才知道收不到。

也就是说：**新用户装完 Anycast，第一件事就是按 `Alt+Space` 发现没反应，而且看不到任何提示。**
这不是一台机器的问题，是选键的问题。所以默认值也换。

### 换成什么、为什么

| 候选 | 结果 |
| :--- | :--- |
| `Alt+Space` | 被 PI-Desktop 的钩子吞（§12.2） |
| `Alt+Shift+Space` | 同样被吞（同一个钩子按 `Alt` 位匹配） |
| `Ctrl+Alt+Space` | `err=1409`，已被别人用 `RegisterHotKey` 占住 |
| **`Ctrl+Alt+Q`** | `注册=True err=0`，**`WM_HOTKEY=True`** ← 采用 |

避开的三类：系统键、**输入法切换键**（`Ctrl+Space` / `Win+Space` —— 中文环境下尤其不能选）、
IDE 常用键（`Ctrl+Shift+Space`）。

### 改动点

- `src/core/settings.rs::default_wake_hotkey()` → `"Ctrl+Alt+Q"`
- `ui/components/settings_modal.slint` 的 `wake-hotkey` 初值同步（**两处必须一致**，
  否则后端同步过来之前会先闪一下旧键名）
- 设计文档两处「默认 `Alt+Space`」的表述
- `doc/检索增强与判断模型接入开发文档.md` §18.4 补更正说明（那条结论只在
  host-core 没在跑时成立）

### 验证：**把 `wake_hotkey` 字段整个抽掉**，看新默认值是否真的生效

不能只测「配置里写了 `Ctrl+Alt+Q` 能用」——那只验证了配置，没验证默认值。
做法是把字段从 `config.json` 里删掉，让 serde 回落到 `default_wake_hotkey()`：

```
[A] 唤起：起始 visible=False → 按一次 → visible=True    ✅
[B] 收起：置前成功=True visible=True → 按一次 → False   ✅
[C] 再唤起：按一次 → visible=True                        ✅
```

设置页截图同时确认键帽显示 `Ctrl+Alt+Q`（该值来自代码默认，配置里并没有这个字段）。

> ⚠️ **判据的坑**：`toggle_window()` 的语义是「**可见且在前台** → 隐藏；否则 → 显示」。
> 所以「窗口可见但不在前台」时按键只会把它拉到前面，**可见性不变** ——
> 拿「按一下可见性必翻转」当判据，会把正确行为报成失败（本机就报错过一次）。
> 探针必须**先确认置前成功**再按键，且不能用 `rt_probe.py keys`（它自己会 `ShowWindow`）。

### 对老配置的影响

`#[serde(default)]` 只在**字段缺失**时生效，所以已存在 `config.json` 里的
`wake_hotkey` 不会被改动 —— 老用户保留自己当前的值（包括 `Alt+Space`）。
这是刻意的：**不静默改用户的键位**。他们随时可以点键帽重录，或点「检测」看它是否真能送达。

### 为什么没去改 PI-Desktop 那边

PI-Desktop 的插件启动器**目前对用户毫无用处**：`plugins/installed/` 与
`plugins/disabled/` 都是空的，按下去只弹一个「暂无可直接打开面板的插件。」的空面板。
按「谁在浪费这个键」算，该让的是 PI。

但它把这个绑定存在自己的数据库/运行时状态里（`%APPDATA%\PI-Desktop` 下
搜不到任何明文 `openPluginLauncher` / `Alt+Space` 配置项），
从外部改属于动别人的数据，超出本次范围。**留作可选项**：
若用户更想保住 `Alt+Space`，就去 PI-Desktop 的
「设置 → 快捷键 → 插件启动器」里禁用。


## 12.4 「检测」的结论会被自己的 `hide_on_blur` 吃掉（2026-09-25）

§12.1 刚给唤醒键加了「检测」入口，本节就是它的收尾：**这个入口有一条必然踩到的坑**。

### 现象

点「检测」→ 窗口消失 → 什么也不说。用户连「正在检测…」都看不到（那条 Toast 也画在窗口里）。

### 为什么这条链路必然踩到

自检要**真注入一次按键**（§12.1 的设计）。如果这个键被别的程序用键盘钩子吞了，
那个程序会**弹出自己的窗口** —— 它就是在等这个键 —— 焦点随即被抢走，
`hide_on_blur` 把 Anycast 藏起来。

而结论是画在窗口里的：`toast()` 见窗口不可见就把它存进 `pending_toast`，
等下一次 `show_window()` 才补显。

最糟的是：**这次的结论恰恰就是「键坏了」**。所以用户连「按热键把窗口叫回来」
这条退路都没有 —— 唤醒键本身就是坏的那个。

### 这是漏了一道早就存在的闸

同族的「快捷直达」测试按钮（`on_hotkey_test`）一直有这道闸，注释写得明明白白：

```rust
g.state.borrow_mut().suppress_blur = true;   // 测热键会让对方弹窗抢焦点
match g.core.test_hotkey(id.as_str()) { ... }
slint::Timer::single_shot(1500ms, ... suppress_blur = false ...);
```

新加的唤醒键「检测」忘了照抄。

### 复现（PI-Desktop 已退出，自己把机制装回来）

PI 的 host-core 已经不在了，钩子没了 → 没法用它复现。但**要测的是机制**，
所以在探针进程里自己装一个真的 `WH_KEYBOARD_LL`（判据照抄 PI：
只看 `VK_SPACE` + `LLKHF_ALTDOWN`，不查其它修饰键），再用一个自造窗口抢焦点。

脚本：`D:/tmp/hook_swallow.py`（装钩子）+ `D:/tmp/hideblur_verdict_loss.py`（主流程）。
条件：`wake_hotkey = "Alt+Space"`、`hide_on_blur = true`。

### 修复前（真机）

```
t=0.00s 点了「检测」 visible=True
t=0.15s 抢焦点 成功=True 前台=0x1006ac
t=0.40s visible=False
t=0.80s / 1.20s / 1.80s / 2.20s  全部 visible=False
钩子命中 2 次                       ← 目标相确实注入了 Alt+Space，而且被吞了
```

* `prefix_pre.png`（隐藏期间抓图）：抓到的是**背后的 IDE** —— 没有任何结论。
* 卸掉钩子、按唤醒键把窗口叫回来之后，结论才出现（`prefix_post.png`）。

**这条同时自证了机制**：结论能在「叫回来之后」补显，说明它回来时窗口确实不可见
→ 走的正是 `pending_toast`。反过来说，若结论是在隐藏**之前**到达的，
`pending_toast` 会是空的，补显就什么都不会有 —— 所以补显这件事本身就是证据。

### 修法（三处，缺一不可）

1. **自检期间按住失焦隐藏** —— 窗口不藏，结论就正常显示；
2. **结论回来时把窗口重新拉回最前** —— 不然结论是「画在窗口里、但被对方挡着」，
   等于没说；这一步同时让 `poll_tick` 不再判成失焦（前台变回自己了）；
3. **结论显示期间续期**（Toast 寿命 2600ms，续 3s）—— 少了这一步，
   对方窗口再次拿到前台时，下一次 `poll_tick`（200ms 一跳）会把窗口连结论一起藏掉，
   结论显示不到半秒。

新增 `UiState::suppress_blur_until: Option<Instant>`，**用截止时刻而不是布尔量**：
`suppress_blur` 是布尔量，一旦某条路径忘了复位（或结论因为线程 panic 没回来），
`hide_on_blur` 就**永久失效**，而且没有任何报错。截止时刻是**自愈**的 ——
到期自动失效，最坏情况只是多按一会儿。

判据抽成纯函数 `blur_suppressed(flag, until, now)` 并配 3 个用例：
`now < until` 写成 `until < now` 会让它**立刻**失效，属于只能靠用例拦的静默失效。

⚠️ `report_wake_delivery` 里 `force_foreground` **必须先确认窗口可见**：
它内部是裸的 `ShowWindow(SW_SHOW)`，窗口真被藏起来时它只把原生窗口亮出来、
Slint 侧的 `is_visible()` 仍是 false —— 用户会看到一个**空窗口**且没有结论，
比什么都不做更糟。

### 修复后（真机，同一脚本、同一配置）

```
t=0.00s 点了「检测」 visible=True
t=0.15s 抢焦点 成功=True 前台=0x506fc
t=0.40s visible=True 前台=0x30390   ← 前置生效：窗口自己回到最前
t=0.80s / 1.20s / 1.80s / 2.20s  全部 visible=True
钩子命中 2 次
```

`postfix_pre.png`：**结论就在屏幕上**，而且设置页也还开着（窗口全程没藏）。
修复前必须手动把窗口叫回来才看得到，现在不用。

### 顺带一条通用判据

**任何会主动造成失焦的「自检 / 测试」动作，都必须先按住失焦隐藏。**
这类动作的副作用（对方弹窗、抢走焦点）恰恰会被 `hide_on_blur` 当成
「用户走开了」，于是把动作自己的结果藏掉 —— 而且被藏掉的往往是**失败**那个结果，
也就是用户最需要看到的那个。

### 探针本身踩的坑（不是产品问题，但会伪装成产品问题）

`show_window()` 会把视图重置回**搜索页**。所以「先用唤醒键把窗口叫出来、
再点设置页里的按钮」这条路必须先**重新打开设置页**。
第一次跑修复后验证就栽在这：钩子命中 **0 次** —— 自检压根没被触发，
因为那一点落在搜索页的空白处。**钩子命中次数是这类探针的关键自检量**：
0 次就说明「被测动作没发生」，此时任何关于结论的观察都是无效的。

### 补充实测：结论到底会不会被对方的窗口挡住

上面修法里有一句「结论回来时把窗口重新拉回最前」，理由是「不然结论被对方挡着」。
这句话**不能靠推理** —— 它取决于两件必须实测的事：本窗口是不是 topmost、
以及**激活窗口能不能压过同样 topmost 的对手**。

脚本：`D:/tmp/zorder_probe.py`（遍历 z 序）、`D:/tmp/activate_vs_topmost.py`。

| 状态 | 结果 |
| --- | --- |
| 干净启动后的显示态 `GWL_EXSTYLE` | `0x198` → **含 `WS_EX_TOPMOST`** |
| 放一个**非** topmost 窗口压在本窗口上 | 本窗口**仍在最上** → 普通启动的程序盖不住它 |
| 放一个 **topmost** 窗口压在本窗口上 | 对手在最上 → **能**盖住 |
| 再**激活**本窗口 | 本窗口**升到对手上面**（两者都是 topmost） |

结论：

* 启动器类程序基本都 topmost（不置顶就盖不住全屏程序），所以**真凶挡得住结论** →
  `report_wake_delivery` 里那次 `force_foreground` 是**必要且有效**的；
* 普通启动的程序挡不住（本窗口自己就是 topmost）→ 所以 `on_hotkey_test` 那条路径
  **不需要**抢前台；抢了反而会把窗口留在最前，挡住用户真正要看的目标程序。

#### 三个探针陷阱（每一个都会给出相反的结论）

1. ⚠️ **`rt_probe.force_foreground` 会摘掉 `WS_EX_TOPMOST`。**
   它内部是 `SetWindowPos(HWND_TOPMOST)` → `SetWindowPos(HWND_NOTOPMOST)`，
   后者把 TOPMOST 清掉；而应用自己的样式校正**只补 `WS_EX_TOOLWINDOW`、不管 TOPMOST**
   —— 被它碰过一次之后，窗口在整个进程生命周期里**都不再是 topmost**，除非重启应用。
   本机实测：`0x198`（含 TOPMOST）→ 被它碰过 → `0x190`（不含）。
   **测「谁盖住谁」时绝不能调它。**
2. ⚠️ **`WindowFromPoint` 不认本进程造的窗口。**
   本机实测：topmost 的探针窗口压着探针点，它返回的却是背后那个最大化的浏览器 ——
   用它判遮挡会得到**完全相反**的结论（本机就这样先得出过一次错的「A 没盖住」）。
   改用**遍历 z 序**。
3. ⚠️ **`GetWindow(GetDesktopWindow(), GW_HWNDFIRST)` 返回 0。**
   它取的是「兄弟」，桌面没有兄弟。起点要用 `GetTopWindow(NULL)`。
   踩到时表现为「遍历走了 0 个窗口」，看起来像「没有任何窗口命中」，
   其实是遍历压根没开始 —— 又是一次「没看到 X」被误读成「X 不存在」。

> 这三条合起来说明一件事：**同一个问题，换个测法就能得出相反的答案。**
> 所以「谁盖住谁」这种结论必须**同时**有正向对照（放一个肯定能盖住的窗口），
> 否则分不清「被测对象没盖住」和「这个测法测不出盖住」。


## 12.5 「快捷直达 → 测试」端到端验收，以及顺带挖出的两个坑（均已修，2026-09-25）

§12.4 末尾那次「补充实测」用的是**合成窗口**（自己造一个 topmost 对手压上来），
只证明了 z 序通则。这一轮把它换成**真实流程**：真点「测试」、真启动目标程序，
看注释里那三句断言是否成立。

### 12.5.1 流程与判据

夹具：往空的 `hotkeys` 表直插一行（收尾删除，可逆）：

| 字段 | 值 |
| --- | --- |
| `target_path` | `C:\Windows\System32\charmap.exe`（字符映射表） |
| `item_type` | `app` |
| `hotkey` | `Ctrl+Alt+F9` |

`charmap` 是经典 Win32、秒出；而且可以**先手动起好**，让 `activate_or_launch`
走 `find_running_window_by_path` 的「已运行 → 前置」快路径（毫秒级）。

| t=0.70s | 是 | **目标程序** | `Anycast(topmost)` / **字符映射表(非 topmost)** |
| t=1.10s | 是 | 目标程序 | 同上 |
| t=1.50s | **否** | 目标程序 | —（本窗口已让出屏幕） |

### 12.5.3 🔴 坑一（探针 bug，最隐蔽）：`ord()` 不是 Windows 虚拟键码

`D:/tmp/hideblur_verdict_loss.py` 里的 `send()` 用
`vk = ord(main.upper())` 把单个字符转成 VK。**只有字母和数字恰好重合**
（`'a'`=0x41=`VK_A`、`'7'`=0x37=`VK_7`），**标点全部错位，而且错到别的键上、不报任何错**：

| 写法 | `ord()` 得到 | 实际是 | 真正的键 |
| --- | --- | --- | --- |
| `","` | `0x2C` | `VK_SNAPSHOT`（PrintScreen） | `0xBC` `VK_OEM_COMMA` |
| `"."` | `0x2E` | `VK_DELETE` | `0xBE` |
| `"-"` | `0x2D` | `VK_INSERT` | `0xBD` |
| `"["` | `0x5B` | `VK_LWIN` ← **会把 Win 键按下去** | `0xDB` |
| `"\\"` | `0x5C` | `VK_RWIN` | `0xDC` |

后果：脚本「按键成功、无异常」，但应用里那个快捷键**就是没反应** ——
于是很自然地反过来怀疑应用有 bug。本轮就这样**误判过一次**：
以为「`Ctrl+,` 打不开设置页」，还去读了 Slint/winit 的源码追 `text` 怎么生成。
真相是探针一直在发 **`Ctrl+PrintScreen`**。

处置：`tools/rt_probe.py` 新增 `vk_for(main)`（先查 `VK` 表，查不到再问 `VkKeyScanW`，
它会连 Shift 状态一起给出），`keys()` 与 `hideblur_verdict_loss.py::send()` 都改走它。
**修好后 `Ctrl+,` 一次就打开设置页了。**

> 教训：**「按键没反应」和「应用没处理」是两件事。**
> 先用一个**确定的对照**（本轮用 `Esc` 能隐藏窗口）证明「窗口级键盘处理确实被调用了」，
> 再去怀疑具体某个键。

### 12.5.4 ✅ 坑二（已修）：激活态一变，DWM 就把原生标题栏画在窗口上

**现象**：主窗口左上角压着一条**浅色原生标题栏**（标准字号写着窗口标题「Anycast」，
高约 43 物理像素），**一直不消失**，直到窗口被 hide → show 一次才自愈。

**触发条件是「激活态发生变化」，与「测试」路径无关**（本节第一版把这两件事绑在一起，
是错的）：

| 方向 | 表现 | 顶带亮占比 |
| --- | --- | --- |
| **失去**激活（前台归别人） | 画上**整条**标题栏 | 99.4% |
| **抢回**激活（点回窗口） | 画上**窄的一条**（约 60px） | 11.7% |

两个方向都**不会自己消失**（实测等到 5s 仍在）。

之所以感觉「只有点测试才看得到」：`hide_on_blur` 默认开，窗口一失焦就被藏掉，
于是「窗口可见 + 前台不是自己」这个状态**只能由 `suppress_blur` 造出来**
（「快捷直达 → 测试」、唤醒自检「检测」）。把 `hide_on_blur` 临时设 `false`
就能反复制造它 —— 本节所有结论都是这么测的。

**量化判据**（不用看图、可复现）：窗口顶部 `y=5..35` 那一带里**亮度 >150 的像素占比**。
干净态 **0.3~0.7%**，整条标题栏 **99.4%**，窄的一条 **11.7%**。
（上一版用的是 420×30 条带的**平均亮度**：干净 44.7 / 残留 241.1 —— 同一现象，
只是「整条」时平均亮度才会冲到 240 附近。占比这个判据对「窄的一条」更灵敏。）
脚本：`D:/tmp/hk_band.py`（时序）、`hk_final_verify.py`（双向）、`hk_flash.py`（时长）。

**已排除的解释**（全部实测过，别再重复走）：

| 假设 | 实测 | 结论 |
| --- | --- | --- |
| 抓图假象（BitBlt/DWM 合成残留） | 同刻 `PrintWindow(PW_RENDERFULLCONTENT)` **画出同一根标题栏** | ❌ 窗口真的长这样 |
| `WS_CAPTION` 被 winit 带回来了 | 残留态 `GWL_STYLE = 0x16070000`（无 `WS_CAPTION`）；`GetClientRect == GetWindowRect`（非客户区 0×0） | ❌ 不是样式位 |

**「事后擦」的手段也全试过**，只有最后一条有效：

| 手段 | 结果 |
| --- | --- |
| `slint::Window::request_redraw()`（应用内重绘） | ❌ 无效 |
| `SetWindowPos(SWP_FRAMECHANGED)`（不改尺寸） | ❌ 无效 |
| `SetWindowPos(SWP_NOCOPYBITS)`（不改尺寸） | ❌ 无效 |
| `InvalidateRect` + `UpdateWindow` | ❌ 无效 |
| `RedrawWindow(RDW_INVALIDATE\|ALLCHILDREN\|FRAME\|UPDATENOW)` | ❌ 无效 |
| **真的改一次窗口尺寸**（`+1px` → 立刻还原） | ✅ **有效**，11.7% → 0.3% |

尺寸扰动**间隔 0 / 20 / 80 / 350 ms 都有效**（背靠背发即可），
`hwnd` 前后都是 `1290x840`，配置零差异。

#### 🔴 还有一个反直觉的前提：**扰动必须从另一个线程发**

在**本线程**（也就是 `poll_tick` 里）发同样两次 `SetWindowPos`，日志显示尺寸确实
`840 → 841 → 840`、两次都返回 `Ok`，但**标题栏不消失**；从**外部进程**发则有效。
差别在 winit 的 `send_event`：事件处理器**已被借用**时（`poll_tick` 正是在 Slint 回调里跑）
它会把 `WM_SIZE` 对应的 `Resized` **缓冲**起来，于是 Slint 那一次 resize 没有真正
走完「重算表面 + 重绘」。换个线程发，消息由窗口消息队列在空闲时派发，
处理器没被借用，路径就正常了。

> 教训：**「同样的调用」不等于「同样的效果」。** 这次的差异不在 API、不在参数、
> 不在窗口，而在**调用发生在哪个线程 / 哪一层回调里**。
> 只对比参数会一直找不到原因。

#### 修法

`UiState.last_fg` 记住上一次 `poll_tick` 看到的「本窗口是不是前台」，
**只要发生变化**（两个方向都要）就调 `theme::nudge_surface(hwnd)` ——
它在另一个线程里做 `+1px` → 还原。`show_window` 里把 `last_fg` 清成 `None`，
免得刚显示完（本来就是新画的一帧）误报一次变化。

**验收结果**：

* 双向反复切换（点窗口 / 点 charmap，各 2 轮）→ **全部 0.3~0.7%，干净**；
* 真实路径（`hide_on_blur=true` + 点「测试」）→ 多数情况下标题栏**一次都不出现**；
  偶尔出现也只到 **≈0.4s**（受 `poll_tick` 200ms 周期 + `SetForegroundWindow` 异步
  的影响），窗口在 1.5s 时隐藏，用户看到的最坏情况是「闪一下」。

**残留（已处理）**：那 ≈0.4s 来自「200ms 轮询才发现激活态变了」。已按下面的
§12.5.5 换成系统事件驱动。

> 为什么值得记：这条**用户可见**（浅色标题栏压在深色面板上很显眼），而且它
> 只在 `suppress_blur` 路径上暴露 —— 日常唤醒完全正常，很容易被当成偶发。
> 更值得记的是**排查方式**：一开始我把它当成「测试流程的 bug」，
> 一直在测试路径里找；把它拆成「可见 + 前台归属变化」这个**状态**之后，
> 才发现触发条件跟测试毫无关系。

### 12.5.5 把发现延迟从 200ms 压到事件级：`SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`

§12.5.4 的修法是对的，但**发现**「激活态变了」靠的是 200ms 轮询 —— 所以擦除动作
最坏要等 200ms 才发生，用户看到的是「闪一下」。这一节把它换成系统事件驱动。

链路（三跳，每跳只加一件事）：

| 层 | 做什么 |
| --- | --- |
| `core::win_thread` | 系统消息线程上 `SetWinEventHook(EVENT_SYSTEM_FOREGROUND, …, WINEVENT_OUTOFCONTEXT)`，回调里发 `SysEvent::ForegroundChanged` |
| `core` | 原样转成 `BackendNotification::ForegroundChanged`（**不掺和判断**） |
| `gui` | 收到后调 §12.5.4 那个 `nudge_if_activation_changed()` |

**轮询**留着当**兜底**，不是冗余：out-of-context 钩子在消息队列拥塞时会被系统丢弃，
只靠它可能整场收不到；有轮询在，最坏情况也只是退回装上钩子之前的水平，不会更差。

#### 三个设计决定（都不是随手写的）

**① 回调**绝不能**碰 `STATE`（`RefCell`）**

钩子回调可能在 `handle_commands` **持有 `STATE` 可变借用期间**被派发 ——
`handle_commands` 里有 `SendInput`（投递自检注入按键），而注入按键会改前台窗口，
前台变化正是这个钩子监听的事件。那时再 `STATE.with(|s| s.borrow())` 就是重入
同一把 `RefCell` → **panic**。所以回调走独立的
`static EVENT_HANDLER: OnceLock<SysHandler>`（`Send + Sync`），整条路径不碰 `RefCell`。

**② 钩子只报「前台变了」，**不判**「是不是本窗口」**

回调拿到的 `hwnd` 是**新的前台窗口** —— 别人抢焦点时它是**对方**，跟我们要判的
「**本窗口**是不是前台」不是一回事。判据只有 GUI 那份 `last_fg` 有，就让它一家判，
免得两处判据迟早走样。所以 `ForegroundChanged` 刻意**不带字段**。

⚠️ 由此也**不能**用 `idprocess` 过滤：`EVENT_SYSTEM_FOREGROUND` 是由
「变成前台的那个窗口」所属进程产生的 —— 按本进程 PID 过滤，**只能收到「抢回激活」，
收不到「失去激活」**；而后者恰恰是画**整条**标题栏（99.4%）的那个方向。

代价说清楚：没有过滤 ⇒ **系统里任何窗口切换都会往 Slint 事件循环投一次事件**。
这是刻意接受的 —— 那条路径只做「比一下 `last_fg`」，而且**事件循环本来就被
200ms 的 `poll_timer` 每 5 秒唤醒 25 次**，多这几下是噪声级别。
真要省，正确的做法是**在回调里**用 `IsWindowVisible(本窗口)` 挡一道
（看不见就没有要擦的东西），而不是按 PID 过滤 —— 后者会把「失去激活」整条砍掉。

**③ 新增 `blur_will_hide` 闸：马上要被藏掉的窗口**不擦

有了即时通知，通知会在 `poll_tick` 把窗口藏起来**之前**到达 —— 于是「用户点开别的
窗口」这条**最常发生**的路径上会多出一次擦除：纯亏，而且是在窗口即将消失时给它来
一次 `+1px` 抖动。所以擦之前先问一句「这个窗口马上会被失焦隐藏收掉吗」，
判据与 `poll_tick` 里那道隐藏闸**同一个方法**（`Gui::blur_will_hide`），
不是各写一套。

⚠️ 但**只跳过扰动，不跳过 `last_fg` 的更新**。若连 `last_fg` 一起跳过，
「用户点走 → 隐藏真正发生前又点回来」这个竞态里那条「中间变过一次」的线索就丢了，
画上的标题栏会一直留着 —— 正好是本函数要修的那个 bug。
