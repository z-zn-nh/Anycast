## 2. 渲染与亚克力：实测结论（重要）

在本机（Windows 11 26200，NVIDIA 显卡，150% 缩放）逐一实验后的结论：

| 方案 | 结果 |
| :--- | :--- |
| Slint 默认 Skia（wgpu / D3D12 HWND 交换链） | 窗口完全不透明（交换链仅支持 Opaque Alpha） |
| Skia-OpenGL、FemtoVG（WGL） | 整个窗口不可见（疑为 NVIDIA “DXGI 分层呈现”导致） |
| **软件渲染器（softbuffer，预乘 BGRA）** | **半透明正常，当前默认** |
| DWMWA_SYSTEMBACKDROP_TYPE + ExtendFrameIntoClientArea(-1) | 客户区几乎全透明，内容消失 |
| SetWindowCompositionAttribute(ACRYLICBLURBEHIND) | 忽略客户区 Alpha，窗口变为不透明黑块 |
| winit 透明窗口机制 | 用空区域调用 `DwmEnableBlurBehindWindow`，系统 backdrop 不再绘制 |

因此当前默认：软件渲染器 + DWM 圆角 + 深色模式，**透光但无模糊**。两种系统级方案保留为实验开关：`ANYCAST_ACCENT=1`、`ANYCAST_DWMSBT=1`；渲染器可用 `SLINT_BACKEND=winit-skia-opengl` 等覆盖。

> **⚠️ 以上结论已于 2026-09-23 修订，见第 6 节。** 系统级 Acrylic 已改为默认启用，
> 并补上了此前完全缺失的 `WS_THICKFRAME` 准入样式修复。

软件渲染器的已知限制：`drop-shadow` 系列属性不生效（右键菜单、筛选浮层的投影不会绘制）。

### 若需要真实“毛玻璃”效果的候选方案

1. **显示时抓屏 + 自行模糊**：窗口显示前截取其背后的屏幕区域，降采样后做 2~3 次盒式模糊并着色，作为窗口背景图。不依赖 DWM 与显卡驱动，符合设计文档“视觉类似 Haze，不要每帧全窗口 Blur”的要求。代价是每次唤起约 10~30 ms 且背景为静态快照。
2. **DirectComposition 交换链**：需要绕开 Slint 的 wgpu 表面创建流程，工作量大，暂不建议。

## 3. 另一个已修复的启动时序问题

首次 `show_window()` 在 Slint 事件循环启动前执行，此时 winit 窗口尚未创建，`window_handle()` 为 None，导致 DWM 效果与前置聚焦从未应用。现改为 `finish_native_show()` 以单次定时器重试直至拿到 `HWND`。

## 6. 构建故障根因与亚克力修复（2026-09-23）

### 6.1 构建「卡死无输出」的真实原因：rustc 内存耗尽

此前多次出现 `cargo build` 长时间无输出、后台任务一直 running 却拿不到结果。
经排查，根因是 **rustc 因内存耗尽崩溃**，而非锁冲突或工具链损坏。

- 本机 24 逻辑核心 / 32GB 内存，cargo 默认按核心数**并发起 24 个 rustc**；
- Slint 依赖链（skia / icu / windows-sys）单个 rustc 的 LLVM 峰值内存很高，并发打满即耗尽内存；
- 铁证日志：`rustc-LLVM ERROR: out of memory`、`memory allocation of 524288 bytes failed`。

**连带产生的误导性错误**（排查时极易带偏方向）：
崩溃的 rustc 会在 `target/` 留下残缺中间产物，后续编译随即报出数百条与真实原因无关的假错误：

```
only metadata stub found for `rlib` dependency `core`
can't find crate for `std`
cannot find macro `println` in this scope
exit code: 0xc0000409, STATUS_STACK_BUFFER_OVERRUN
```

**结论：见到「std / core 找不到」这类错误，先查 OOM，不要重装工具链。**

**修复措施：**

| 措施 | 说明 |
| :--- | :--- |
| 新增 `.cargo/config.toml` | `[build] jobs = 2`。实测 j=24 必崩、j=8 仍在 hashbrown / windows-sys 处 OOM、**j=2 稳定**。⚠️ **该结论已被 2026-09-24 的修订推翻，jobs 现为 1**，见第 7 节 |
| 删除冗余 `target2/` | 之前用 `CARGO_TARGET_DIR` 绕锁的产物，导致依赖编译两遍且加剧冲突 |
| 清除残留锁文件 | `.cargo-lock` / `.cargo-build-lock` / `.cargo-artifact-lock` |
| 重装 `rustc` + `rust-std` 组件 | 修掉 `STATUS_STACK_BUFFER_OVERRUN` |

**结果：299 个依赖全部编译通过，0 错误，耗时 7m43s。**

> ⚠️ 一个已澄清的误判：`.rlib` 体积小于同名 `.rmeta` **不是损坏**。
> 新版 rustc 采用元数据分离布局（rlib 只存目标代码，完整元数据在 .rmeta），属正常形态。

### 6.2 亚克力背景：三重阻断的修复

设计稿 65.2 指出的三条阻断，此前只有「实验开关」级别的实现，默认路径下等于未生效。

**修复 1：补回 DWM 准入窗口样式（此前完全缺失）**

新增 `theme::ensure_dwm_admissible()`：用 `SetWindowLongW` 为无边框窗口补回
`WS_THICKFRAME | WS_CAPTION | WS_SYSMENU`，再以 `SetWindowPos(SWP_FRAMECHANGED)`
触发 DWM 重算帧架构。**DWM 对不含 `WS_THICKFRAME` 的裸窗口会拒绝注入系统材质**，
这正是此前「API 调用成功但毫无效果」的原因。

**修复 2：系统级 Acrylic 改为默认启用**

原实现只在 `ANYCAST_DWMSBT=1` 时才启用 DWM 背景材质，默认状态下既无 DWM 模糊、
又只有软件渲染器输出的半透明底色 —— 观感是「透光但无模糊」。
现改为默认走 `DWMSBT_TRANSIENTWINDOW` + 客户区帧扩展，并在失败时回退到
`SetWindowCompositionAttribute(ACRYLICBLURBEHIND)` 兜底。

同时新增「系统透明效果开关」探测（读注册表 `EnableTransparency`）：
当系统关闭透明效果时不走 AccentPolicy 兜底，避免退化成不透明黑块。

**诊断开关**（正常使用无需设置）：
`ANYCAST_NO_ACRYLIC=1` 完全禁用系统材质；`ANYCAST_NO_STYLE=1` 跳过样式补全；
`ANYCAST_ACCENT=1` / `ANYCAST_DWMSBT=1` 仅走单层，用于 A/B 对照。

**运行验证日志：**
```
[INFO anycast::gui::theme] DWM 系统级 Acrylic 已启用（DWMSBT_TRANSIENTWINDOW）
```

### 6.4 首次启动置顶预置

新增 `AppCore::seed_default_pins_if_needed()`，在应用扫描完成后执行：

- 按关键词从**已扫描到的真实应用**中挑选，最多 4 个，因此不依赖用户具体装了什么；
  关键词按优先级：`windows terminal` → `terminal` → `powershell` → `command prompt`
  → `git bash` → `visual studio code` → `vscode` → `cursor` → `anycast`；
- 每个关键词取**名称最短**的匹配项，以优先命中规范入口
  （例如「Command Prompt」优先于「Developer Command Prompt for VS 2022」）；
- 由配置项 `pins_seeded` 保证只执行一次，用户日后手动清空置顶不会被重新灌入；
- 若扫描未匹配到任何应用，**不写标记**，留待下次启动重试；
- 已存在置顶（如从旧版本升级）时只补标记，绝不覆盖用户数据。

GUI 侧 `RecentItemsReady` 处理器已一并补上 `refresh_pinned()`，
否则预置卡片要等下次交互才出现。

### 6.5 视觉验证方法与新增工具

在沙箱/非交互环境下验证桌面 GUI 有两个坑，本次一并解决：

1. **应用扫描返回 0 个**：shell 里的 `ProgramData` / `APPDATA` / `PUBLIC` 可能为空，
   导致开始菜单扫描不到任何目录。启动时显式传入真实路径即可：

   ```bash
   APPDATA="C:\\Users\\30130\\AppData\\Roaming" \
   ProgramData="C:\\ProgramData" \
   PUBLIC="C:\\Users\\Public" ./target/debug/anycast.exe
   ```

2. **目标窗口被遮挡或已隐藏**：`screenshot.ps1` 是抓全屏，抓到的是前台窗口。
   新增 `tools/win_shot.ps1`，一次调用完成
   「按标题找窗口 → `SW_RESTORE` → `HWND_TOPMOST` 置前 → 抓该窗口屏幕区域」，
   中途不会因焦点变化导致目标窗口跑掉：

   ```powershell
   & "D:\Anycast\tools\win_shot.ps1" -title "Anycast" -out "D:\Anycast\target\x.png" -scale 1.0
   ```

   想要验证网格视图时，直接改 `%APPDATA%\Anycast\data\config.json` 的
   `view_mode`（`list` / `grid`）再重启即可，无需模拟点击。

**验证结论**：列表视图与网格视图均已与设计稿对齐；置顶预置产出 4 张常用卡片；
`DWM 系统级 Acrylic 已启用（DWMSBT_TRANSIENTWINDOW）`；索引 48032 个文件耗时 10.4s。

## 7. 主窗口退出任务栏 / Alt+Tab（2026-09-24）

### 现象

打开 Anycast 后任务栏多出一个 Anycast 按钮，与「居中的浮动搜索面板」定位不符
（设计文档第 7 节明确要求「不是传统应用窗口」）。

### 根因：窗口样式有两层，此前只处理了其中一层

| 层 | 决定什么 | 项目现状 |
| :--- | :--- | :--- |
| `GWL_STYLE` | 标题栏、边框、能否缩放 | `no-frame: true` → winit 剥掉 `WS_CAPTION` / `WS_THICKFRAME`；随后 `theme::ensure_dwm_admissible` 又**补回** `WS_THICKFRAME` 以换取 DWM 材质准入 |
| `GWL_EXSTYLE` | **任务栏按钮、Alt+Tab 归属** | **全项目从未设置过** |

`WS_EX_TOOLWINDOW`（工具窗口，不进任务栏 / Alt+Tab）与 `WS_EX_APPWINDOW`
（强制出现在任务栏）都在**扩展样式**里，与 `no-frame` 完全无关。
两者都没动 → Windows 按默认规则给这个顶层窗口分配了任务栏按钮，
按钮图标取自 `ui/main.slint:37` 的 `icon: Icons.tray`，观感上像凭空多出一个 App。

补充前提：Slint 1.18 的 `.slint` 语言层**没有** skip-taskbar 类属性
（`i-slint-compiler` 的 `builtin_elements.rs` 里窗口只有 `no-frame` / `always-on-top` /
`icon` / `title` 等），所以这件事只能在 Rust 侧用 Win32 补。
另注：winit 0.30 的 `with_skip_taskbar(true)` 走的是 `ITaskbarList::DeleteTab`，
**只去任务栏、保留 Alt+Tab**，与本次要的效果不同。

### 修复

- `src/gui/theme.rs` 新增 `hide_from_taskbar(hwnd)`：置 `WS_EX_TOOLWINDOW`、清 `WS_EX_APPWINDOW`。
  ⚠️ 任务栏只在窗口**可见性变化**时重新评估，单纯改样式按钮不会当场消失，
  因此函数内补一次 `ShowWindow(SW_HIDE)` → `ShowWindow(SW_SHOWNOACTIVATE)`；
  用 `NOACTIVATE` 避免抢焦点（前置聚焦仍由 `launcher::force_foreground` 单独负责）。
- `src/gui/mod.rs` 新增 `Gui::fix_taskbar()`，在 `finish_native_show()` 拿到 HWND 时调用
  —— 该处已有「拿不到 HWND 就重试」的时序处理，直接复用。
  ⚠️ **必须每次显示都调用**，不能加「只做一次」的守卫：一次 `hide()` → `show()` 之后
  winit 会把窗口属性重置回默认值，任务栏按钮就复活了。详见 §10。

### 代价（预期内，已与用户确认）

窗口不再出现在 **Alt+Tab**。唤醒方式只剩托盘图标与全局唤醒热键（默认 `Alt+Space`）。
若将来要「只去任务栏、保留 Alt+Tab」，改用 `ITaskbarList::DeleteTab` 即可，不动扩展样式。

诊断开关：`ANYCAST_KEEP_TASKBAR=1` 保持原样，用于 A/B 对照。

### 验证工具

`GWL_STYLE` / `GWL_EXSTYLE` 位，判定是否已退出任务栏。

### ⚠️ 编译环境：真凶是「提交限制」，不是并发数

本次 `cargo build` 连续失败于 `rustc-LLVM ERROR: out of memory`。
**根因修正**：`.cargo/config.toml` 里「并发数 × 单 rustc 峰值」的旧结论只是表象，
真正的约束是 Windows 的**提交量（commit）余量**：

| 指标 | 数值 |
| :--- | :--- |
| 物理内存 | 31.74 GB 总 / **9.9 GB 可用**（看着宽裕） |
| 提交上限 | 39.74 GB |
| 已提交 | 37.0 GB |
| **剩余提交余量** | **仅 2.4 GB** ← 撞的是这堵墙 |
| 历史峰值 | 39.74 GB（正好等于上限） |

- 提交上限 = 物理 31.74 + 页面文件 8。注册表 `PagingFiles` 里配了
  `D:\pagefile.sys 49152 49152`，但**该文件不存在**（D 盘还有 144GB 空闲），
  而 `ExistingPageFiles` 把它列了出来——**该值会骗人**。本该有 ~87GB 上限。
- 依赖已全部编好、只剩 bin crate 时，`jobs` 不再起作用（瓶颈是单 rustc 的 ~2GB 峰值）。
  **有效手段是 `-j 1`**：`jobs=2` 时 rustc 从 jobserver 拿 2 个令牌、最多 2 个 LLVM
  上下文同时驻留，`-j 1` 压到 1 个。实测 `jobs=2` + `debug=0` + `opt-level=0` 仍 OOM，
  补上 `-j 1` 才通过（2m02s）。
- 各手段实测：`opt-level=0` 有效（2.19→1.87GB）；`debug=0` **基本无效**（2.15→2.19GB）；
  `CARGO_INCREMENTAL=0` 略有帮助且不牵连依赖。
- OOM 崩在 codegen 途中会写坏 `target/debug/incremental`，链接期随即报
  `LNK2019 无法解析的外部符号` × N + `LNK1120` —— **全是假错误**，
  只删该目录（1.0GB）即可，不必全量重编。

新增 `tools/build_mem_probe.py`：跑一次编译并每秒采样 rustc 提交量与系统余量，
最后打印峰值，用来判断"要腾出多少提交量"。
（写此类探针**必须把子进程输出重定向到文件**，用 `subprocess.PIPE` 后等进程结束再读会因
cargo 输出超 64KB 管道缓冲区而死锁——实测卡死 16 分钟，且症状酷似"残留锁阻塞"。）

### 顺带发现 → 已裁决移除（2026-09-24）

`minimize_to_tray` 是**死开关**：`src/core/settings.rs:93` 有字段、设置面板有开关、
`src/gui/mod.rs:1017` 写回配置，但**没有任何窗口逻辑读它**。

深挖后确认它比「没人读」更彻底 —— **它背后的功能根本不存在**：

- 窗口是 `no-frame: true`，没有系统标题栏最小化按钮；`.slint` 里搜 `minimize`
  只命中设置面板那一行开关，即**没有任何最小化入口**
- 唯一的隐藏入口 `hide_window()` 无条件执行 `ui.hide()`，也就是说程序**一直**在
  「隐藏到托盘」（关闭即隐藏、托盘保活、热键或托盘唤出），开关并不参与门控
- 而任务栏按钮已在第 7 节移除，所以「关掉开关 → 不隐藏到托盘」这条路会把窗口
  彻底弄丢 —— 托盘是现在唯一常驻的锚点

**裁决（爽世）：移除开关。** 已删除 `settings.rs` 的字段、`mod.rs` 的
`set_minimize_to_tray()` 同步调用与 `set_setting_bool()` 里的 `"minimize_to_tray"` 分支、
`settings_modal.slint` 的属性声明与 `FluentSwitch` 行；原位置改为一行说明文字
「常驻系统托盘 —— Anycast 不占用任务栏与 Alt+Tab；关闭窗口即隐藏至托盘，
点托盘图标或按唤醒热键唤出」。

兼容性：旧 `config.json` 里的 `minimize_to_tray` 键会被静默忽略 —— `AppSettings`
用的是逐字段 `#[serde(default)]` 且未开启 `deny_unknown_fields`，无需迁移。

### 构建配置：`[build] jobs` 由 2 固化为 1

`.cargo/config.toml` 里原本是 `jobs = 2`，但第 7 节已实测证明

```toml

```

**等效性验证**（此前怀疑 `[build] jobs` 与命令行 `-j 1` 因 jobserver 令牌机制而"不完全等价"，

```
→ Finished in 2m49s，EXIT=0，13 条 warning，无 OOM
```

**结论：两者在本项目等效**，日常直接 `cargo build` 即可。
`D:\pagefile.sys` 修好后可把 `jobs` 改回 2~6 提速（实测 24 必崩、8 仍会 OOM）。

## 8. 修复：从脚本启动时应用扫描静默返回 0 个（2026-09-24）

### 现象

验证任务栏改动时，程序日志出现 `应用扫描完成：0 个`（文档记录为 136 个），
而文件索引正常（`48097 条`）。差点被误判成扫描逻辑坏了。

### 根因：环境变量「存在但为空串」

`src/core/apps.rs` 的 `scan_dirs()` 原实现：

```rust
if let Ok(pd) = std::env::var("ProgramData") {
    dirs.push(PathBuf::from(pd).join("Microsoft\\Windows\\Start Menu\\Programs"));
}
```

**`std::env::var` 对已设置但为空的变量返回 `Ok("")`，不是 `Err`。** 不判空就会拼出
`Microsoft\Windows\Start Menu\Programs` 这个**相对路径**，而 `scan_apps()` 里
`if !dir.exists() { continue; }` 直接跳过 —— 静默返回 0 个。

从 shell / 脚本 / 计划任务 / 工具链启动时，`APPDATA=`、`ProgramData=`、`PUBLIC=`
经常是空串。对照实验：

| 启动环境 | 应用扫描结果 |
| :--- | :--- |
| 三个变量为空串 | **0 个** |
| 补齐三个变量 | **136 个** |

### 修复

`src/core/apps.rs`：

1. 新增 `known_folder(&FOLDERID_*)`：用 `SHGetKnownFolderPath` 取系统已知文件夹，
   **不依赖环境变量**（`CoTaskMemFree` 已配对释放）。
2. 新增 `env_dir()`：`std::env::var(...).ok().filter(|s| !s.is_empty())`，过滤空串。
3. `scan_dirs()` 改为**已知文件夹优先、环境变量兜底**，覆盖
   公共开始菜单 / 用户开始菜单 / 用户桌面 / 公共桌面四处。
4. 目录列表为空时 `log::warn!`，把静默失败变成可诊断。

### 验证

| 启动环境 | 修复前 | 修复后 |
| :--- | :---: | :---: |
| 三个变量为空串 | 0 个 | **134 个** |

（134 vs 旧实现读环境变量时的 136，差 2 个，未深究——两个数都属正常范围。）

### 备注

这类「从脚本启动 → 环境变量为空串 → 静默失败」的坑是通用的，已沉淀为
skill `windows-launch-env-gotchas`（含无头读窗口样式做验证的做法，
避免被 `hide_on_blur` 干扰截图）。

## 9. 修复：候选截断会整档吃掉高分文件（2026-09-25）

### 现象

搜索命中数较多的关键词时，**一批本该排在最前面的文件整档消失**。

真机复现（本机 4.8 万文件，查询 `anim`）：总命中 223 条，其中**以 `anim` 开头**的
有 40 个 —— 这 40 个是 `name_score` 里 85 分的「前缀匹配」档，本该占据前 40 名，
实际**一个都进不了前 50**（实测 0/40）。

### 根因：SQL 的排序键与 Rust 的打分不是一回事

链路是两段排序：

1. `storage::search_files` 取候选：`ORDER BY length(f.name) ASC, f.mtime DESC LIMIT ?`
2. `search::search_files` 重排：`name_score()` 打分 → 稳定排序 → 取前 50

`name_score` 的前三档是**常数分**（精确 100 / 前缀 85 / 词首 70），只有第四档
（包含）是 `55 − 长度×0.2`。而 SQL 那边**只有长度**这一个键 —— 等于拿「名字短」
当「相关度高」的代理。

于是第四档里大量名字很短的「包含」匹配，会把第一/二档里名字较长的文件整体挤出
`LIMIT` 之外。Rust 侧再准也没用：**它看不到这些文件**。

注意第二段排序是 `slice::sort_by`（**稳定排序**），同分元素保持 SQL 给的顺序 ——
所以只要候选集正确，最终顺序就是对的，问题**只在候选集**。

### 修复

**① SQL 加档位排序键（核心）**

```sql
ORDER BY CASE
    WHEN lower(f.name) = ?               THEN 0   -- 精确
    WHEN lower(f.name) LIKE ? ESCAPE '\' THEN 1   -- 前缀
    ELSE 2 END ASC,
  length(f.name) ASC, f.mtime DESC LIMIT ?
```

精确/前缀匹配无条件排在最前，截断只可能落在「其余」档内部 —— 而那一档的分数随
名字长度单调递减，与 `length ASC` 方向一致，所以截断是安全的。

**② 候选上限 100 → 3000**（`search::FILE_CANDIDATE_CAP`）

档位键覆盖不到「词首档（70 分）」—— 在 SQL 里表达「按分隔符切词后某段以 q 开头」
要枚举分隔符，太脆弱。改用「候选取得足够多」来覆盖。本机实测除 `png`(1.5 万命中) /
`jpg`(1 万) 这类极端查询外，命中数都远低于 3000。

**③ 先排序、后构造 item**

候选从 100 涨到 3000 的前提是**不能**对全部候选构造 `SearchItemModel`
（`file_to_item` 要 clone path / name / subtitle）。改为先用纯函数算分排序，
只给选中的前 50 条构造。

**④ 使用统计批量化（顺带修掉一个性能坑）**

`boost_by_usage` 原先对**每个候选项**打 2 条 SQL（`recent_stats` + `is_pinned`）——
100 候选就是 200 条 SQL，涨到 3000 会直接拖垮每次击键。改为 `Storage::usage_stats()`
一次读全（`recent` 表本身有 200 行上限、`pins` 更小）。`idle_items` 里逐条查
`is_pinned` 的 60 次 SQL 也一并收掉。

### 验证

**① 回归测试（含变异测试）**

新增 `core::search::tests::prefix_match_survives_candidate_truncation`：造 120 个
短名字的「包含」匹配 + 1 个长名字的「前缀」匹配，断言后者排第一。

把代码**临时改回旧行为**重跑，该测试如期变红 —— 证明它不是摆设：

```
test core::search::tests::prefix_match_survives_candidate_truncation ... FAILED
前缀匹配的长名字被候选截断吃掉了（这正是旧实现的缺陷）；实际返回 50 条
```

另新增 `usage_bonus_matches_applied_bonus`，守住「排序用的分」与「写回的分」两份
公式不漂移（这类不一致不会有任何编译期或运行期报错）。

全量 `cargo test`：**90 passed / 0 failed**（原 88 + 新增 2）。

**② 真库验证**（4.8 万文件，Python 直接跑同一条 SQL）

| 查询 | 总命中 | 前缀档 | 旧：进前 50 | 新：进前 50 |
| :--- | ---: | ---: | ---: | ---: |
| `anim` | 223 | 40 | **0** | **40** |
| `chat` | 293 | 14 | 13 | 13 |
| `2026` | 893 | 16 | 3 | 3 |

**③ GUI 端到端**：输入 `anim`，列表顶部即 `anime4k_shaders` + `Anime4K_*.glsl` 系列
（85 分前缀档），滚到底部是 `shootAnim` 系列（`shootanim` 整串一个词，落 53 分包含档）
—— 排序梯度完整，整档 40 个文件全部可见。

**④ 诚实的边界：触发条件比想象中窄**

- 任取 55 个「命中 100~1500 条」的查询，修复前后**前 50 条完全一致（55/55）** ——
  因为前缀档本身超过 50 个时，它们本来就排不进前 50，截断与否不影响可见结果。
- 在 32 个「前缀档 ≤ 50 个」的查询里，**只有 1 个（`anim`）**发生实质变化。

所以这是**低频但一旦触发后果严重**的缺陷：不是少显示一两条，而是**整档高分文件消失**。
另外叠加使用加成后（`boost_by_usage` 最多 +45 分），一个用户常用但名字较长的文件
会被截断挡在门外 —— 这条路径在当前 `recent` 只有 1 行的库上还测不出来。

### 成本

档位键要对每一行求值 `lower(f.name) LIKE 'q%'`，最重的查询有感知
（Python 口径的 SQL 取数耗时；Rust 侧更快，且取数只是整个搜索耗时的一部分）：

| 查询 | 命中 | 旧 | 新 | 差 |
| :--- | ---: | ---: | ---: | ---: |
| `png` | 15413 | 7.4ms | 16.8ms | +9.4ms |
| `jpg` | 10040 | 6.4ms | 12.8ms | +6.4ms |
| `chat` | 293 | 0.4ms | 0.5ms | +0.1ms |

轻查询基本无变化；极端查询 +10ms 相比 400ms 防抖可忽略。

### 未做

- **词首档（70 分）没有专门的 SQL 表达**，仍靠 3000 的候选上限兜底。要彻底解决得在
  SQL 里表达「按分隔符切词」，收益不抵复杂度。
- **同档内没有区分度**：85 分档里 100 个文件之间只按长度排。用户想找的若恰好是其中
  较长的一个，仍要靠使用加成或补全更多字符。这是 `name_score` 分档粒度的固有局限，
  不在本次修复范围。

## 10. 修复：一次 hide/show 之后窗口样式被 winit 重置（2026-09-25）

### 现象

§7 的「退出任务栏 / Alt+Tab」与 §6.8.1 的「DWM 准入样式」都**只在首次显示时校正一次**
（`Gui::fix_taskbar` 开头是 `if state.taskbar_fixed { return; }`）。
于是 —— **用户按一次唤醒热键（或关窗到托盘再唤出）之后，两处修复同时失效**：

- 任务栏重新冒出 Anycast 按钮
- 右上角重新出现 `—` `□` `×`，`×` 压在筛选漏斗上（设计稿 65.2 的「漏斗套叉」脏图）

两次修复各自都「验过」，但都只验了**首次显示**那一帧，于是谁也没发现它们在第二次显示时
就已经不生效了。

### 根因：winit 在 `hide()` 时把窗口属性重置回默认值

不是系统慢慢改回去，而是**在隐藏那一刻同步发生**的。

### 复现证据（旧二进制，实测）

探针 `tools/win_style_probe.py`：读两层样式位，**同时读 `IsWindowVisible`**
（样式位正确而窗口隐藏 = 假阳性，所以两者必须一起看）。

热键临时改为 `Ctrl+Shift+Space` —— `Alt+Space` 家族合成按键打不进去（见 §「唤醒热键」
一节的排除结论），要验等价行为必须换组合键。

| 时刻 | `visible` | `GWL_STYLE` | `GWL_EXSTYLE` |
| :--- | :--- | :--- | :--- |
| 首次显示 | True | `0x16070000` ✓ | `0x00000198` ✓ |
| 发键一次（→ 隐藏） | False | `0x06CF0000` ✗ | `0x00040118` ✗ |
| 再发一次（→ 唤出） | True | `0x16CF0000` ✗ | `0x00040118` ✗ |

- `WS_CAPTION`(0x00C00000) / `WS_SYSMENU`(0x00080000) 回来了 → DWM 会画标题栏按钮
- `WS_EX_TOOLWINDOW`(0x80) 掉了、`WS_EX_APPWINDOW`(0x40000) 置上了 → 任务栏按钮复活
- **第三次读数证明旧代码补不回来**：`taskbar_fixed` 已为 `true`，`fix_taskbar` 直接早退

截图 `_probe_style_broken.png`：右上角 `— □ ×` 清晰可见，`×` 与漏斗图标重叠。

### 修复

- `theme.rs`：从 `hide_from_taskbar` 拆出 `enforce_taskbar_exclusion` ——
  只写扩展样式位、**不做 hide/show**（无闪烁），幂等早退
- `mod.rs::fix_taskbar`：**去掉「整个函数只做一次」的守卫**，每次显示都跑；
  原 `taskbar_fixed` 降级为「是否首次」的判据，只用来选任务栏那条路径的版本
  （首次走 `hide_from_taskbar`，带 `SW_HIDE + SW_SHOWNOACTIVATE` 逼任务栏重新评估，
  代价是一次可见闪烁；此后走无闪烁版）
- `ensure_dwm_admissible` 本来就幂等（`new_style == style` 早退），每次调用无成本

> **教训**：`if 已修复 { return; }` 这类「只做一次」的守卫，在 winit 下是**错的**——
> winit 会在可见性变化时重新应用窗口属性。凡是对 HWND 属性做的手工校正，
> 都必须假设它随时可能被重置。

### 验证（修复后，同一探针、同一路径）

编译后重启应用，重复上面的读数：

| 时刻 | `visible` | `GWL_STYLE` | `GWL_EXSTYLE` |
| :--- | :--- | :--- | :--- |
| ①首次显示 | True | `0x16070000` ✓ | `0x00000198` ✓ |
| ②发键一次（→ 隐藏） | False | `0x06CF0000` ✗ | `0x00040118` ✗ |
| ③再发一次（→ 唤出） | True | **`0x16070000` ✓** | **`0x00000198` ✓** |

- ② 的偏离是**预期内**：`hide_window()` 不走校正路径，窗口反正不可见，样式坏不坏无所谓
- ③ 才是判据：**唤出后样式被补回来了**。修复前同一时刻是 `0x16CF0000` / `0x00040118`
  （`WS_CAPTION|WS_SYSMENU` 在位、`WS_EX_APPWINDOW` 在位），补不回来
- 连按 2 轮（累计 3 次 hide/show）全部符合期望 → **可重复**
- 截图 `_probe_style_fixed.png`：右上角只剩筛选漏斗图标，`— □ ×` 已消失
  （对照 `_probe_style_broken.png`）
