## 2. 判断模型事实层

### 2.1 Jev（云端，闭源）

TypeSafe AI 出品（创始人 Diogo Almeida，前 OpenAI，InstructGPT / RLHF 论文共同作者），
2026-09-15 发布，官方称第一个公开的「System One」模型。

| 约束 | 数值 / 说明 |
| :--- | :--- |
| 输出 | `Choice`（选一个）/ `Score`（打分）/ `Noul`（0~1 概率），均带置信度 |
| 延迟 | 端到端 **70~500 ms** |
| 成本 | 输入 **$0.042 / M token**，输出免费 |
| 候选上限 | **255** |
| 输入 | 仅文本；**无状态**（不记忆历史） |
| 中文 | 官方标注 CJK「可用但准确率不等同英文」 |
| 可用性 | 节点集中在美国西海岸，**中国大陆无法直接使用** |
| 权重 | **闭源**，仅 API |
| 准确率 | **不高于大模型**：TypeSafe 自评 67.8% vs 基线 74.1%；Banking77 实测 81.0% vs Claude Opus 5 84.4% |

#### 2.1.1 Jev API 接入规格（已查证官方文档）

**端点**：`POST https://api.typesafe.ai/v1/systemone`
**鉴权**：`Authorization: Bearer $TYPESAFE_API_KEY`（官方 SDK 从环境变量 `TYPESAFE_API_KEY` 读取）

```jsonc
{
  "model": "jev-latest",              // 生产建议锁定版本，如 "jev-1.13.0"
  "state": "找一下昨天改的 docker 配置",  // 字符串 / JSON 对象 / 文本数组
  "questions": {
    "type": {
      "type": "choice",
      "instructions": "用户想找的东西属于哪一类？",
      "criteria": { "document": "文档、笔记、说明", "code": "源代码、配置" }
    },
    "time": { "type": "score", "instructions": "时间范围？",
              "criteria": ["今天", "昨天", "本周", "更早"] },
    "is_search": { "type": "noul",
                   "instructions": "这是在搜索本机文件吗？" }
  }
}
```

**三种问题类型的写法差异（容易踩坑）**：

| 类型 | `criteria` 形式 | 约束 |
| :--- | :--- | :--- |
| `choice` | **映射**（key → 描述） | 最多 **255** 个选项 |
| `score` | **有序数组**（2~10 个等级描述） | 返回可能带小数的 score + 完整分布 |
| `noul` | **不需要** | 仅 `instructions`，返回 0~1 概率 |

**响应**：

```jsonc
{
  "model": "jev-1.13.0",
  "answers": {
    "type":      { "type": "choice", "choice": "code", "confidence": 0.96,
                   "probabilities": { "document": 0.04, "code": 0.96 } },
    "time":      { "type": "score", "score": 1.0, "confidence": 0.91,
                   "legend": { "0": "今天", "1": "昨天" }, "probabilities": { "1": 0.91 } },
    "is_search": { "type": "noul", "noul": 0.98 }
  },
  "usage": { "input_tokens": 434, "output_tokens": 75 }
}
```

**限制与最佳实践**：

- 速率：**250,000 tokens/秒** 与 **1,200 请求/分钟**
- 上下文：state + 全部问题 ≤ **64k token**；state + 单个最长问题 ≤ **32k**
- **把多个问题批量放进一次调用**（并行执行、共享 state 成本），不要拆成多次
- 阈值重要时**锁定版本号**，`jev-latest` 行为可能变化
- 用 `confidence` 做三档路由：高置信自动执行 / 中置信升级 / 低置信回退

**可用性（实测）**：官方端点 `api.typesafe.ai` 与第三方托管端点
`jevtypesafeai.com/api/v1/decide`（`jv_live_` key，免排队）**经 Clash `127.0.0.1:7897` 均可达**，
返回标准 401 结构。即：**中国大陆经本地代理可用。**

**探针脚本**：`tools/jev_probe.py` —— 用本项目真实查询（中文 / 英文 / 混合 / 纯关键词 / 非检索）
测槽位解析效果与延迟，**带期望值对照**，跑完直接给出分组准确率，可导出 markdown 报告。

```bash
# 官方端点（TypeSafe 排队申请）
set TYPESAFE_API_KEY=ts_...
python tools/jev_probe.py --proxy http://127.0.0.1:7897

# 第三方托管端点（jv_live_ key，免排队）
set JEV_API_KEY=jv_live_...
python tools/jev_probe.py --endpoint hosted --proxy http://127.0.0.1:7897

# 只看用例清单 / 只跑指定用例 / 导出报告
python tools/jev_probe.py --list
python tools/jev_probe.py --only zh1,en1
python tools/jev_probe.py --report doc/jev-实测报告.md
```

**12 个用例的期望值设计**（这是「结果如何」的判据，不是拍脑袋）：

| 组 | 用例 | 必判对的槽位 |
| :--- | :--- | :--- |
| 中文 | zh1 找一下昨天改的 docker 配置 | is_search=1, type=code, time=yesterday |
| | zh2 那个写存储逻辑的文档 | is_search=1, type=document |
| | zh3 我的项目文件夹在哪 | is_search=1, type=folder |
| | zh4 上周下载的那个压缩包 | is_search=1, type=archive, time=last_week |
| 英文 | en1 / en2 / en3 | 同构的 time / type 槽位 |
| 混合 | mix1 找 Dockerfile 昨天改的 | is_search=1, type=code, time=yesterday |
| 关键词 | kw1 docker / kw2 storage.rs | is_search=1, **is_natural=0** |

#### 2.1.2 Jev 实测结果（2026-09-24，真实数据已跑通）

**Key 已拿到，12 用例 × 5 轮全部成功。** 报告见
`doc/Jev实测报告-措辞修正前.md` 与 `doc/Jev实测报告-措辞修正后.md`。

**准确率：只改措辞，77% → 96%**

| 分组 | 修正前 | 修正后 |
| :--- | :--- | :--- |
| 中文 zh | 8/10（80%） | **10/10（100%）** |
| 英文 en | 5/7（71%） | **7/7（100%）** |
| 混合 mix | 3/3（100%） | 3/3（100%） |
| 关键词 kw | 2/4（50%） | 3/4（75%） |
| 非检索 neg | 2/2（100%） | 2/2（100%） |
| **合计** | **20/26（77%）** | **25/26（96%）** |

**改了什么？** 只改了 `is_search` 的 `instructions` 措辞 —— 模型、输入、参数全没动。

- 旧：「这个输入是在**搜索**本机的文件或文件夹吗？（而不是闲聊、提问或执行命令）」
- 新：「用户是否**在找**本机的某个文件或文件夹？只要输入像是在找东西就算
  —— 包括只给一个单词、一个文件名或一个名词短语。」

**为什么影响这么大**：旧措辞被模型理解成「这是不是一个明确的**搜索指令**」，
于是把「提问」和「指代短语」都排除了：

| 输入 | 旧 is_search | 新 is_search |
| :--- | :--- | :--- |
| 我的项目文件夹在哪 | 0.29 ❌（这是提问） | **0.93** ✅ |
| 那个写存储逻辑的文档 | 0.30 ❌（这是指代） | **0.60** ✅ |
| files I modified yesterday | 0.44 ❌ | **0.85** ✅ |
| the doc about storage logic | 0.33 ❌ | **0.59** ✅ |

`is_natural` 也顺带修好（旧措辞把「名词短语」排除在外，而名词短语恰是最典型的搜索输入）：
en1 **0.46 → 0.95**、en2 0.42 → 0.92、en3 0.49 → 0.96。

> **关键教训：判断模型的准确率高度依赖问题措辞，不是「接上就能用」。**
> `instructions` 必须按真实场景反复校准 —— 这与 §2.3 说的「零样本接近瞎猜」是同一件事。

**逐槽位表现（修正后）**

| 槽位 | 表现 | 说明 |
| :--- | :--- | :--- |
| `type` | **7/7 = 100%** | 中文 / 英文 / 混合全对，置信度多为 1.00 |
| `time` | **5/5 = 100%** | yesterday / last_week 全对 |
| `is_search` | 11/12 | 唯一错的是 kw1 `docker`（0.38） |
| `is_natural` | 分离度良好 | 自然语言 0.92+，纯关键词 0.09~0.15 |

> **`kw1 docker` 判错无害**：单个通用词在**闸门 1（本地规则）**就被拦下、
> 根本不会调用模型。模型自己给的 `is_natural=0.15` 也说明它认得这是关键词。
> 真正要防的是**假阳性**（把闲聊判成搜索）—— 实测 **0 个**。

**延迟（5 轮，剔除首轮冷启动）**

| 指标 | 实测 |
| :--- | :--- |
| min | **约 750 ms**（这是下界） |
| p50 | 约 900 ms |
| max | 2.2 ~ 3.9 s（正常）；**首轮冷启动 15.1 s** |
| 平均 | 1.0 ~ 1.5 s |

> ⚠️ **这推翻了 §5.7 原先写的「200~460 ms」与「超时 800 ms 放弃」**：
> - 延迟**下界就有 750 ms**，`p50` 已到 900 ms —— 800 ms 超时**会砍掉一半请求**
> - 超时阈值应提到 **2000 ms**，并保留硬超时
> - 首轮 15 秒说明**冷启动极慢**，必须预热，或首屏绝不等待
> - 「先出本地结果、异步补充」因此**从优化变成了必需**

**结论：Jev 可用，但必须满足三个前提**
1. `instructions` 按真实场景校准过（否则只有 77%）
2. 异步调用 + 2000 ms 硬超时 + 首屏不等
3. 默认关闭，由用户显式开启（§5.7 三级闸门）

### 2.3 官方承认的三个短板（本项目必须处理）

1. **零样本接近瞎猜**：基础 checkpoint 在 typed-decisions 零样本只有 **0.362**
   （随机基线 0.318、多数类 0.461）。那个 0.766 是**微调后**的成绩。
   → **不微调直接用，等于没用。**
2. **选项超过 20 个就崩**：所有选项共享固定 `head_max_len`（英文 192 / 多语言 256 token），
   77 个选项摊到每个只剩 3~4 token，Banking77 的 0.425 就是这么来的。
   → **选项必须控制在 20 以内**（本项目槽位设计远低于此，见 §5.3）。
3. **出厂过度自信**：英文版温度重拟合前 ECE 0.466；多语言版出厂压根没拟合。
   → **必须按（题型 × 选项数）重新拟合温度**，否则置信度门禁不可信。
   另：`score` 是最弱原语（SST-5 仅 0.372），算术 / 计数 / 日期比较**不要交给它**。

> ### ⚠️ 由此得出的定位修正（重要）
>
> 原方案把「结果重排」也交给判断模型。**数据不支持这个做法**：
> `search relevance` 仅 **0.628**、`response quality scoring` 仅 **0.581**，

>
> **修正后的职责划分**：
>
> | 职责 | 由谁承担 | 依据 |
> | :--- | :--- | :--- |
> | 意图解析（类型 / 时间 / 位置槽位） | ✅ **Laya** | intent and routing 0.991 |
> | 查询路由（极速 / 智能） | ✅ **Laya** | 同上 |
> | **结果重排打分** | ❌ **本地排序算法** | search relevance 仅 0.628 |
> | 算术 / 计数 / 日期比较 | ❌ **确定性代码** | score 原语最弱 |
>
> 即：**Laya 只负责「听懂」，不负责「排名」。**
> 这让它的职责更窄、更可靠，也正好避开它最弱的两项能力。

> **重要**：`position_embedding_type = "sans_pos"` —— 用 **RoPE** 而非可学习位置嵌入表，
> 因此**序列长度是动态的**，ONNX 导出对动态轴非常友好（无需固定 max_len 的 embedding 表）。

**`multilingual/tokenizer/tokenizer_config.json`（关键字段）**
```json
{ "tokenizer_class": "PreTrainedTokenizerFast", "model_max_length": 8192, "padding_side": "right" }
```
> **重要**：是 **fast tokenizer**，`tokenizer.json`（实测 34,363,188 B ≈ 34.4 MB）
> **可被 Rust `tokenizers` crate 直接加载**，运行时无需 Python。

**仓库文件清单结论**：**无 ONNX 文件**；决策头逻辑在 Python 代码里
（`rl_agent_api.py` / `rl_common.py`）。**Rust 落地需自备一次性导出脚本。**

### 2.5 决策模型结构（读 `rl_common.py` 得出）

```
h = encoder(input_ids, attention_mask).last_hidden_state   # ModernBERT 22 层，768 维
h = h + type_emb(qtype)                                     # nn.Embedding(3, 768)  ← 一行查表
h = head(h, src_key_padding_mask=pad)                       # 2 层 TransformerEncoderLayer（全序列自注意力）
m = gather(h, marker_pos)                                   # 每个选项取自己的 [MASK] 标记位
logits = scorer(m)                                          # LayerNorm → Linear(768,768) → GELU → Linear(768,1)
logits = masked_fill(~marker_mask, -1e4)
# act_head（"直接作答 vs 升级"）：pooled + [top1, top1-top2, 熵, k/255]
#                                 → Linear(772,256) → GELU → Linear(256,2)
```

序列构造（`build_sequence`）：

```
[CLS] "<type> question: <instructions>" [SEP] [MASK]opt0 [MASK]opt1 … [SEP] <state> [SEP]
                                                ↑ markers 记录每个 [MASK] 的位置
```

#### 4.1.2 「`files` 只有 1 行」的根因（2026-09-24 定位完毕）

这不是数据损坏，是**两个缺陷叠加**的必然结果。把库里仅存的 1 行与 543 条正文
放在一起看，线索就完整了：

- 唯一那行是 `…\nt_qq\nt_data\log\qq-log_…qqxlog`，**按遍历顺序排在 543 个
  Emoji 文件之后**；
- 543 条正文全部来自 `…\nt_data\Emoji\…\lottie\*.json`。

**遍历走到了末尾、正文阶段又完整跑完了** —— 也就是说「全量扫描」本身是成功的。
那么 `files` 为什么是空的？因为**中途有人把它清空了**：

```rust
// 旧 rebuild()：先清空，再调 full_scan
let _ = this.storage.clear_files();
...
this.full_scan();

// 旧 full_scan() 第一句：
if self.stats.scanning.swap(true, Ordering::SeqCst) {
    return;                      // ← 已有扫描在跑 → 直接返回，重扫根本没发生
}
```

启动扫描还没跑完时用户点了「重建索引」→ 索引被清空、重扫被静默跳过 →
正在跑的那轮扫描继续往库里写。清空发生在遍历将尽处，于是只剩尾部那 1 条写回；
而正文队列是清空前就攒好的，正文阶段照常把 543 条全部写入。

这一条链同时解释了三件事：`files`=1、`content_fts`=543、以及
**53 MB 空闲页**（`DELETE FROM content_fts` 删掉的是 543 × 每条约 1.4 MB 的
trigram 索引；`files_fts` 的 rebuild 又发生在空表上，所以它的索引页只剩 1 页）。

**而这一切之所以容易撞上，是因为初次扫描太慢** —— 见下。

#### 4.1.3 初次扫描慢的真凶：`has_content()` 全表扫描

```rust
// 旧 has_content()
SELECT 1 FROM content_fts WHERE path = ?1 LIMIT 1
```

`path` 是 `content_fts` 的 **UNINDEXED** 列，该查询只能扫描 FTS5 内容表。
实测查询计划：

```
SCAN content_fts VIRTUAL TABLE INDEX 0:
```

而它在**遍历期对每一个可索引文件都要调用一次**（判断是否已有正文、要不要入队）。
`content_fts_content` 把 `path` 与 `body` 存在同一行，正文单条可达 200 KB ——
未命中时要读完整个内容表才能确定「没有」。

改成查 `content_meta`（`path` 是主键）后，这一步从全表扫描变成主键命中。

#### 4.1.4 另一处静默性能坑：`LIKE` 前缀查询不走索引

对账需要「取某目录的全部后代」。两种写法的实测查询计划：

| 写法 | 查询计划 | 结论 |
| :--- | :--- | :--- |
| `path LIKE 'dir\%' ESCAPE '\'` | `SCAN files USING COVERING INDEX` | **全表扫描** |
| `path GLOB 'dir\*'` | `SEARCH files USING … (path>? AND path<?)` | **范围查找** |

`LIKE` 默认大小写不敏感，SQLite 无法把它改写成范围查找；`GLOB` 大小写敏感，
可以被改写。代价是 GLOB 没有转义符，通配符只能靠字符类 `[*]` 表达。
实现已统一改用 GLOB（见 `storage::glob_descendants`）。

#### 4.3.2 引入的四条（含落地方式）

**① 增量对账取代全量重扫** —— 收益最大的一条

问题：`Indexer::start()` 每次都跑 `full_scan()`，4.8 万文件要 **10.4 秒**。

Everything 靠 USN Journal，但**读 USN 需要管理员权限**（`indexer.rs` 开头已注明），
与「绿色免安装、非特权运行」的定位直接冲突。所以改用**目录 mtime 对账**。

**实测依据（2026-09-24，本机 NTFS）** —— 目录 mtime 的语义：

| 操作 | 目录 mtime |
| :--- | :--- |
| 创建 / 删除 / 重命名**直接**子文件 | **变** |
| 创建**直接**子目录 | **变** |
| **修改子文件内容** | **不变** |
| **孙目录里建文件** | **不变**（不向上传播） |

**这两条"不变"正是我们要的**：只索引文件名的场景下，
「目录 mtime 未变」⟺「该目录的直接子项集合未变」→ 可整棵跳过；
而「改内容不改 mtime」意味着**写文件不会误触发重扫**。

**实现要点（2026-09-24 已落地）**

```
reconcile(dir, mem):                       # mem: path → mtime_ns 快照，常驻内存
    fs_mtime = metadata(dir).mtime_ns
    changed  = mem[dir] != fs_mtime        # 快照缺失 ⇒ 视为变化（首次即全量）
    枚举 dir 的直接子项                     # 无论是否变化都要枚举，否则找不到子目录

    if changed:
        existing = SELECT … WHERE parent = dir      # 走 idx_files_parent
        对每个子项：与 existing 的 (is_dir, mtime_ns, size) 逐项比对
            不一致 → upsert；可索引的文本文件入正文队列
        existing 中磁盘上已不存在的 → 连子树一起删
        mem[dir] = fs_mtime                 # 仅在本轮写入无失败时登记
    for sub in 子目录: recurse(sub, mem)     # 必须递归：孙项变化不向上传播
```

三处关键设计：

1. **用 `mtime_ns` 而非秒级 `mtime`。** 秒精度下「同一秒内先建后删」会得到相同的值，
   变更会被永久漏掉。为此 `files` 表新增 `mtime_ns` 列。
2. **新增 `parent` 列并建索引。** 取直接子项是本算法的比对基准，
   而 `path LIKE 'dir\%'` 走不了索引（§4.1.4），必须靠 `parent = ?` 精确命中。
3. **目录自身的行始终刷新。** 目录数量远少于文件，代价可忽略；
   但它是下一轮能「整棵跳过」的前提 —— 否则快照会一直是旧值，每次都要重做。
4. **路径分隔符必须先规范化。** `read_dir` 给出的子路径是反斜杠，
   而用户配置 / 命令行传入的根目录可能是正斜杠（`C:/Users/...`）。
   不统一的话根目录行存成 `C:/x`、子项的 `parent` 却算出 `C:\x`，
   两者对不上 → 对账会把整棵子树当成「新增」反复重写。
   已统一在 `indexer::norm_path` 处理（Windows 文件名不含 `/`，替换安全）。

成本从「读 4.8 万个文件的 metadata 并逐个写库」降到
「枚举目录 + 只对变化目录写库」。

**兜底**：Windows 的目录 mtime 是 lazy 更新，且少数程序（某些 git 操作）
可能不更新它。因此保留**每 10 分钟一次**的自动对账，
以及设置页的手动「重建索引」作为最终手段。
`notify` 负责秒级实时，定时对账负责覆盖休眠唤醒 / 监控丢失 / 进程被强杀期间的变更。

**⚠️ 必须承认的盲区：改文件内容不会改变目录 mtime**

上面那张语义表里「修改子文件内容 → 目录 mtime 不变」既是优点也是缺点：

- 优点：写文件不会误触发重扫（这正是我们能跳过整棵子树的依据）；
- 缺点：**该文件自己的 mtime / size 变了，对账却看不到** ——
  目录 mtime 一致就整目录跳过了，库里那条记录停在旧值。

实测确认（合成目录树，40 目录 / 600 文件）：

| 轮次 | 操作 | 目录访问/变化 | 耗时 |
| :--- | :--- | :--- | :--- |
| 1 | 空库首次全量 | 81 / 81 | 1.02 s |
| 2 | 无任何变更 | 81 / **0** | **10.5 ms** |
| 3 | **改写 1 个文件的内容** | 81 / **0** | 9.8 ms |

第 3 轮正是这个盲区：内容确实变了，对账却完全没看见。

**真实规模实测**（2026-09-25，本机 5 个索引根目录，含 OneDrive 与 E: 盘）：

| 轮次 | 操作 | 目录访问/变化 | 索引文件 | 正文 | 耗时 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | 空快照首次全量（正文索引开） | 5230 / 5221 | 48268 | 609 | 84.79 s |
| 2 | 无任何变更 | 5230 / **0** | 48268 | 609 | **1.38 s** |

第 2 轮只读了 5230 个目录的 metadata 就收尾，**不写一行库** —— 61× 提速，
且这是 **debug 构建**（`[build] jobs = 1`），release 只会更快。
两轮的「丢弃条目」均为 0、「孤儿正文」均为 0、一致性正常。

> 验证方式：`anycast.exe --index-scan --db <副本> --root ...`（见 §8 命令行入口）。
> 全程在**数据库副本**上跑，未触碰真实库。

影响面：**文件名检索不受影响**（名字没变，而 `files_fts` 只索引文件名）；
受影响的是搜索结果里显示的修改时间 / 大小、按时间排序、以及正文检索。

**三层兜底**：

| 层 | 触发 | 覆盖什么 |
| :--- | :--- | :--- |
| `notify` 实时 | 秒级 | 应用**运行期间**的一切变更，含内容改写 |
| 增量对账 | 每 10 分钟 | 应用未运行期间的**增 / 删 / 改名** |
| **全量校验**（新增） | 每 24 小时 | 应用未运行期间的**内容改写** |

全量校验（`REQ_FULL`）与「重建」的区别：**它不清空索引**，
只是强制检查每个目录的子项。逐项比对仍会跳过真正没变的行，
所以一次全量校验只写「确实变了」的那些 —— 不是把 4.8 万行全部重写一遍。

实现上扫描等级分为四档，取较高者优先、不排队：

```
REQ_NONE < REQ_RECONCILE < REQ_FULL < REQ_REBUILD
```

**② 元数据常驻内存**

现在 `search_files()` 走 SQL（FTS5 MATCH + JOIN + `ORDER BY length(name), mtime DESC LIMIT ?`），
返回后 Rust 层**又**用 `name_score()` 重新打分排序 —— **两次排序**。
更糟的是 SQL 的 `LIMIT` 在**错误的排序**下截断，**可能漏掉真正的高分结果**：
名字长但前缀匹配（score 85）的，会被名字短但中间匹配（score 55）的挤出去。

4.8 万条 × 约 216 B ≈ **10 MB**，完全放得下内存。改为内存索引后：
一次遍历 + 一次排序，无 SQL 往返。

**保护**：若 `index_roots` 被设成整个盘（可能 50 万+ 条 → 100 MB+），
需设条目上限，超出则降级回 SQLite 路径。

**③ rename 事件迁移 `pins` / `recent`**

`file_to_item()` 用 `format!("file:{}", f.path)` 作 id —— **文件一改名，id 就变**，
`pins.item_id` / `recent.item_id` 全部断链（**置顶项凭空消失**）。

拿 FRN 需要 `CreateFile` + `GetFileInformationByHandle`，全量扫描时是 4.8 万次文件打开，
**成本远超收益**。更轻的替代：`notify` 的 rename 事件本来就带**新旧两个路径**
（`EventKind::Modify(ModifyKind::Name(RenameMode::Both))`，`event.paths = [from, to]`）。
现在 `handle_fs_event()` 把它当「from 不存在 → 删」+「to 存在 → 加」处理，
**没有迁移引用**。补一段：识别 rename → 把 `pins` / `recent` 的旧 id 改成新 id。
**零额外成本。**

> ⚠️ 待验证：`notify 8` 在 Windows 上 rename 事件是否**稳定**给出 `RenameMode::Both`
> 与两个路径（有时只给 `From` 或 `To`）。实现前需先实测。

**④ 索引可重建 + 引用方自愈**

`rebuild()` 已能清空重扫，符合「索引是派生物」。但**引用方没有自愈**：
`clear_files()` 之后，`pins` / `recent` 里指向文件的 `file:xxx` id 全部悬空，
而 UI 仍会渲染它们。

补：重建后扫一遍 `pins` / `recent`，把目标已不存在的条目**标记为失效**
（而非直接删除 —— 万一只是外接盘没插）。惰性清理：使用时发现文件不在就移除。

#### 4.3.4 顺带发现的实现缺陷（已全部修复，2026-09-24）

**① 「重建索引」会清空索引却不重扫 —— 本机数据库损坏的直接原因**

```rust
// 旧 rebuild()：先清空，再调 full_scan
let _ = this.storage.clear_files();
...
this.full_scan();

// 旧 full_scan() 第一句：
if self.stats.scanning.swap(true, Ordering::SeqCst) {
    return;                      // ← 已有扫描在跑 → 直接返回
}
```

清空发生在调用方线程、重扫却可能被跳过，两者不是一个原子动作。
详细推导见 §4.1.2。

**修复**：`rebuild()` 只登记请求（`request_scan(REQ_REBUILD)`），
真正的清空由索引线程在扫描开始时执行 —— 清空与重扫在同一线程内串行，不可能错开。

**② `batch.clear()` 位置错误 —— 扫描会静默丢数据**

```rust
if batch.len() >= 500 {
    if self.storage.upsert_files(&batch).is_ok() {   // 失败时什么也不做
        ...
    }
    batch.clear();          // ← 无论成功失败都清空
}
```

`upsert_files` 失败（磁盘满、DB 被锁、schema 冲突）时，这 500 条**被静默丢弃**，
既不计入统计也不报错，事后无从察觉。

**修复**：失败时先重试一次；仍失败则计数（`IndexStats::dropped`）并写日志，
且**不登记该目录的 mtime 快照**，让下一轮对账自动重试。

**③ `clear_files()` 里的 `rebuild` 是重复劳动**

```sql
DELETE FROM files; DELETE FROM content_fts; INSERT INTO files_fts(files_fts) VALUES('rebuild');
```

`files_ad` 触发器已在 `DELETE FROM files` 时逐行维护了 `files_fts`，
再 `rebuild` 一次纯属重复（4.8 万行还要逐条触发一次删除）。
`rebuild` 的正确用途是**修复已经失同步的索引**，而不是清空 —— 已从清空路径移除。

**④ 任何 `metadata()` 失败都被当成「文件已删除」**

```rust
Err(_) => { let _ = self.storage.remove_path_tree(&path.to_string_lossy()); }
```

OneDrive 占位文件、网络盘抖动、改名事件的旧路径，都会让 `metadata()` 失败 ——
于是**一个瞬时错误 = 整棵子树被从索引里抹掉**。

**修复**：只有 `Remove` 与 `Modify(Name)` 事件才允许按子树删除，
其余情况留给定时对账处理。

**⑤ 每个文件系统事件都无条件重建正文索引**

`handle_fs_event()` 命中可索引文件时直接调 `index_content()`，不看内容是否已经新鲜。
QQ / OneDrive 这类持续触碰文件的目录因此反复「删正文 + 写正文」——
本机库里 53 MB 空闲页正是这么攒出来的。

**修复**：加 `content_needs_update(path, mtime_ns)` 闸门（查 `content_meta` 主键），
mtime 未变就不读盘、不重建。

## 5. 判断模型接入设计（Laya 为主）

### 5.1 定位：只做两件事（已按 §2.3.1 修正）

```
用户输入
   │
   ├─ ① 意图解析（Choice / Noul）→ 槽位：类型 / 时间 / 位置
   └─ ② 查询路由（Choice）→ 极速 / 智能 / 混合
```

**明确不做**：

- ❌ 不生成关键词（避免幻觉，关键词必须由本地分词产出）
- ❌ 不生成文本、不回答开放问题
- ❌ **不做结果重排打分** —— 官方 `search relevance` 仅 **0.628**、`response quality scoring` 仅 **0.581**，
  明显弱于 `intent and routing` 的 **0.991**。**重排交给本地排序算法**（前缀 > 词首 > 中间 + 频率/时间/类型权重）
- ❌ 不做算术 / 计数 / 日期比较（用确定性代码）

### 5.2 触发策略（省电 + 保速度）

| 输入形态 | 是否触发 | 说明 |
| :--- | :--- | :--- |
| 纯关键词（`docker`、`vs`） | ❌ 永不 | 本地检索直接出结果 |
| 自然语言（含动词 / 时间词 / 疑问词） | ✅ 异步触发 | 「找一下昨天改的 EasyNote 文档」 |
| 用户手动切到「✦ 智能搜索」 | ✅ | 显式意图 |

判定用**本地规则**（正则 + 词表），零成本、零延迟。

### 5.3 意图解析的槽位设计（必须落在 20 选项以内）

| 维度 | 候选选项 | 数量 |
| :--- | :--- | :-: |
| 类型 | 全部 / 文档 / 代码 / 图片 / 音视频 / 压缩包 / 可执行 / 文件夹 | 8 |
| 时间 | 今天 / 昨天 / 本周 / 上周 / 本月 / 今年 / 更早 / 不限 | 8 |
| 位置 | 不限 / 当前目录 / 指定盘符 / 常用目录 | 4 |

> **三个维度分别调用，各自远低于 20** —— 正好落在 Laya 的甜点区。

> **关键设计：关键词不由判断模型生成。**

> 因此**关键词提取必须留在本地**（分词 + 拼音 + 倒排召回），

**示例**：输入「找一下我昨天修改的 EasyNote 文档」


### 5.6 双后端架构（可切换）

需求：**「不妨做两版出来，或者提供给用户选择」**。设计为可插拔后端：

```rust
// src/core/decision/mod.rs
pub trait DecisionBackend: Send + Sync {
    fn id(&self) -> &'static str;          // "rule" | "laya" | "jev"
    fn display_name(&self) -> &'static str;
    fn is_local(&self) -> bool;
    fn is_available(&self) -> bool;        // 权重存在 / API Key 已配置
    fn warm(&self) -> Result<()>;          // 预加载（仅本地模型需要）
    fn decide(&self, state: &str, questions: &[Question]) -> Result<Answers>;
}
```

| id | 实现 | 依赖 | 延迟 | 成本 | 默认 |
| :--- | :--- | :--- | :--- | :--- | :-: |
| `rule` | 纯规则（正则 + 词表 + 日期解析） | 无 | < 1 ms | 0 | ✅ 开 |
| `laya` | 本地 ONNX（`tokenizers` + `ort`） | 约 650 MB 权重 | 200~460 ms | 0 | 关 |
| `jev` | 云端 HTTP | API Key + 代理 | 70~500 ms | $0.042/M | 关 |

设置项（写入设计文档 §25）：

```
AI 后端策略
├── Backend Mode (自动 / 仅规则 / 本地模型 / 云端模型)
├── Local Checkpoint (英文根版 421M / 多语言版 322M / 按查询语言自动)
└── Cloud Fallback (本地低置信时是否升级到云端，默认关)
```

「**自动**」的语义：`rule` → `laya` →（若开启）`jev`，逐级升级，任一级成功即止。

### 5.7 智能调用：三级闸门

需求：**「智能化调用，必要时才使用模型」**。实现为三道闸门：

```
输入
 │
 ├─ 闸门 1 · 本地规则（<1ms，零成本）
 │    纯关键词 / 前缀指令 / 已知模式 → 直接检索，【不调模型】
 │
 ├─ 闸门 2 · 本地模型 Laya（200~460ms，零成本）
 │    规则判定为自然语言 → 【先出本地结果】→ 异步解析槽位 → 二次检索
 │
 └─ 闸门 3 · 云端模型 Jev（实测 p50 ≈ 900 ms，下界 750 ms，低成本）
      仅当「用户显式开启」且「本地置信度 < 阈值」时触发
      【超时 2000 ms 直接放弃，不阻塞】
```

> **2026-09-24 实测修正**（依据 §2.1.2，12 用例 × 5 轮）：
> 原先写的 Jev 延迟「70~500 ms」与「超时 800 ms 放弃」**都偏低**。
> 实测 **min 约 750 ms、p50 约 900 ms、max 2.2~3.9 s**（首轮冷启动 15.1 s）。
> - 800 ms 超时**会砍掉一半请求** → 提到 **2000 ms**
> - 延迟下界就有 750 ms，**「即时」不可能** → 首屏绝不等待模型，只能异步补充
> - 首轮冷启动 15 s → 需预热（应用启动后先发一次空调用），或接受首轮不调模型

三条硬性规则：

1. **首屏永远由本地检索提供**。模型结果只做**增量替换**，不得清空已渲染列表；
2. **任何一级失败或超时 → 静默降级到上一级**，不弹错误提示；
3. **纯关键词输入永不触发闸门 2 / 3**（由闸门 1 的本地规则判定）。
   - 实测佐证：模型对纯关键词自己给出的 `is_natural` 只有 **0.09~0.15**，
     与自然语言的 0.92+ 分离度良好 —— 闸门 1 的规则判定与模型判断一致。

### 5.8 语言策略（回应「搜索大部分文件都是英文」）

> ⚠️ **关键区分：目标文件名的语言 ≠ 用户查询的语言。**

「搜索大部分文件是英文」指的是**目标文件名**（`Dockerfile`、`main.rs`、`docker-compose.yml`）。
但**用户敲进搜索框的查询**完全可能是中文：

| 用户输入（查询） | 命中目标（文件名） | 语言关系 |
| :--- | :--- | :--- |
| 「找一下昨天改的 docker 配置」 | `docker-compose.yml` | **中文查询 → 英文文件** |
| 「那个写存储逻辑的文档」 | `storage.rs` / `architecture.md` | **中文查询 → 英文文件** |
| `docker compose` | `docker-compose.yml` | 英文 → 英文 |

前两行是**跨语言检索**，正是多语言版的价值所在。
**这件事必须实测，不能凭「文件是英文的」推断「查询是英文的」。**

**checkpoint 选择策略**：

| 场景 | 建议 checkpoint | 体积 | 说明 |
| :--- | :--- | :--- | :--- |
| 查询以**英文**为主 | `laya` 英文根版 | 808 MB | 英文任务更准，且无需中文分词 |
| 查询含**中文** | `laya-multilingual` | 647 MB | 覆盖 100+ 语言 |
| 不确定 | **先埋点** | — | 记录真实查询的语言分布再决定 |

> **两个 checkpoint 不要同时加载**（合计约 1.45 GB，违反 §27 内存约束）。
> 官方 `Router` 是「按需切换」，但切换冷启动 7~10 s。
> 本项目改为**用户显式选定一个**，设置页给出上表作为选择依据。

**落地建议（三步走）**：

1. **第一步只做规则版 + 埋点** —— 零成本先跑起来，记录查询语言分布；
2. 拿到分布后再决定装英文版还是多语言版；
3. 若分布混合 → 优先多语言版（英文能力虽略逊英文根版，但覆盖更全）。

### 5.9 关于「若不考虑本地优先，Jev 是否更合适」

诚实评估：**Jev 的优势场景与本项目并不完全吻合。**

| Jev 的优势 | 本项目是否需要 |
| :--- | :--- |
| Banking77 77 类 0.870（宽标签空间） | ❌ **不需要** —— 本项目槽位只有 8 个，用不上多类优势 |
| 零配置、无需微调 | ✅ **需要**（这是 Jev 的真优势） |
| 无需下载权重 | ✅ 需要 |
| 英文强 | ⚠️ 取决于实测（见 §5.8） |
| **中文弱（CJK）** | ❌ **硬伤**（若查询含中文） |
| 需代理 + 网络不确定性 | ❌ 与「快速启动」目标冲突 |

**结论**：Jev 真正的价值是**省掉微调与权重管理**，而不是更准
（§2.1 已述：其准确率并不高于大模型）。

- 若实测确认「查询以英文为主 + 不愿投入微调」→ **Jev 是合理选择**；
- 但只要查询含中文，它的 CJK 短板会直接伤到体验。

**所以双后端是对的**：把选择权留给用户，并用**实测数据**而非猜测来决定默认值。

### 14. 搜索链路消费槽位（2026-09-25 落地）

`AppCore::search` 在**智能模式**下先跑闸门 1（同步 < 1 ms，搜索本身已在后台线程），
把槽位经 `decision/bridge.rs` 落到 `SearchScopeFilter` 上，再交给搜索引擎。

**优先级**：`用户手点的筛选 > 判断模型槽位 > search::parse_intent 词表`

桥接只填**空**的维度 —— 用户显式说了「只看代码」，模型再按「文档」两字
把范围改成 `document` 是在跟用户对着干。

**与 `search::parse_intent` 的分工**（两者都做意图解析，不冲突）：

| | 产出 | 说明 |
| :--- | :--- | :--- |
| `parse_intent` | **关键词** | 模型被明令禁止生成关键词（模块头注释） |
| `bridge` | **筛选范围** | 类型 / 时间 / 位置三个维度 |

重合维度上模型更精确（ISO 周、精确月/年边界、`image` 与 `media` 区分），
所以**模型先落、`parse_intent` 补漏**：后者独有的 `clipboard` / `app` 类型、
`最近` / `近期` 这类相对时间仍然生效。

**位置维度是新增能力** —— `parse_intent` 完全不解析位置。
`rule.rs` 现在会把盘符/常用目录解析成**可直接消费的范围键**
（`drive-d` / `desktop` / `downloads`，与 UI 位置菜单 id 同构），
`LocationSlot::Current` 刻意**不给**范围键：面板是浮动的，
无头状态下无从得知「当前目录」是哪个，编一个出来只会把结果筛空。

**芯片去重**：`parse_intent` 是独立跑的、不看 scope，所以它仍会为同一些维度
产出芯片。桥接认领的维度会把同名芯片剔掉再插到前面 ——
否则会同时显示「类型：图片与媒体」和「类型：图片」两条互相矛盾的提示。

#### 顺带修掉的两个真实缺陷

1. **「昨天」会把今天也算进来**（off-by-one）
   - `SearchScopeFilter::time_upper_bound()` 里有个 `e + 86_399`，
     是给日历选择器的 `to_ts(e)`（当天**零点**）打的补丁 ——
     但 `parse_intent` 传进来的 `day_range()` 已经是当天 23:59:59，
     再补一次就多算一整天。**两处调用方约定不一致，补丁只能打在调用方。**
   - 修法：`custom_end_time` 的约定统一为「**含**当天 23:59:59」，
     `time_upper_bound()` 原样返回；日历侧改为 `to_ts(e) + 86_399`。
   - 实测：`--decide "找一下昨天改的 docker 配置"` → 起点 `09-24 00:00:00`、
     终点 `09-24 23:59:59`，**正好一天**。
   - 回归测试：`models::tests::time_upper_bound_includes_end_day`

2. **`image` / `executable` 槽位会静默不过滤**
   - `storage::type_extensions()` 只认 `document` / `code` / `media` / `archive`。
     判断模型的 `image` / `executable` 落进去返回 `None`，
     `item_in_scope` 走 `_ => None` 分支命中 `unwrap_or(true)` → **一条都不筛**。
     这比不筛更糟：芯片上写着「类型：图片」，看着像筛过了。
   - 修法：给 `type_extensions` 补 `image`（`media` 的精确子集）与
     `executable`（`exe`/`msi`/…，**与 scope 的 `app` 不是一回事** ——
     后者是开始菜单扫描出的应用）。
   - `image` 必须与 `media` 分开，否则「找图片」会把视频也带出来。

### 15. 闸门 2 / 3 接进搜索链路（2026-09-25 落地）

`gui::refresh_search` 现在分两段跑，**首屏绝不等待模型**：

```text
refresh_search
 ├─ ① core.search_gated(req)      闸门 1（同步 <1ms）+ 检索 → 立刻渲染首屏
 │     返回 (SearchResponse, worth_upgrade)
 ├─ ② worth_upgrade == false ?    → 结束（纯关键词输入到此为止）
 ├─ ③ sleep 400ms + 代数检查      用户还在打字 → 结束（防抖，见下）
 ├─ ④ core.upgrade_intent(query)  阻塞、后台线程；失败/超时一律 None
 └─ ⑤ core.search_with_intent()   → gui::merge_upgraded() **增量**插到列表最前
```

**`merge_upgraded` 遵守 §5.7 硬性规则 1**：新条目归入「深度匹配」分组**插到最前面**，
首屏结果一条不动（清空再填会让用户看到闪烁；升级失败时更会让他刚看到的结果凭空消失）。
没有新条目时**什么都不做** —— 连芯片都不动，免得界面「抖一下」却毫无变化。

选中的处理（`plan_merge`）：用户已经用方向键选过了就保住他那一条
（下标位移量是**新条目数**，不是「新条目数 + 1」—— 分组标题只存在于行模型里、不进
`results`，多算一行会选到原本那条的下一条）；还停在第一条就留在新的第一条上。

#### 按范围浏览（browse）兜底 —— 这条路的**唯一**出路

「我前几天弄的那个东西」的本地关键词是「前几天弄」，拿它去检索**永远是 0 条**，
再加多少筛选条件也还是 0 条 —— **筛选只能做减法**。
而模型真正听懂的是「最近一周的代码文件」。

所以：**关键词搜不到东西、但模型给了筛选条件**（`Intent::has_slot()`）时，
丢掉关键词重搜一次，只留范围 + 时间倒序。实测效果：

```text
输入：我前几天弄的那个东西            （智能模式）
首屏：0 条（关键词「前几天弄」无匹配）
模型：type=code  time=last_week
结果：深度匹配 → C:\...\VasUpdateSystem\bubble\*.config.json（上周的代码文件）
```

只在**升级路径**上做，且只在**一条都没有**时做：首屏绝不走这条路
（必须快、必须由关键词驱动），已经有结果时也不动（那说明关键词有效）。

#### 防抖：不做的话每敲一个字都要花钱

实测发现的真实缺陷：原来的实现**每个击键都会发一次云端调用** ——
打字途中会有多个请求在途（实测 POST 计数确认）。
Jev 单次 p50 ≈ 900 ms 且按次计费，敲 20 个字符就是 20 次调用。

修法：发起闸门 2/3 之前先 `sleep(400ms)` 再检查查询代数，代数变了就直接返回
（`query_gen` 因此从 `AtomicU64` 改成 `Arc<AtomicU64>`，好让工作线程也读得到）。
**实测：10 个字符的输入只产生 1 次调用。**

首屏仍然逐字符刷新（本地、免费），只有升级被防抖。

#### API Key 用 `TextInput.input-type` 遮蔽

#### ⚠️ 排查记录：一度误判成 Slint 双向绑定失效

现象：Key 框里明明有内容（能看到圆点），点「保存」却弹**「已清空本地 Key」**，
配置里存的是空串。当时推出「Rust 侧的 `set_*` 会打断 `<=>` 双向绑定」这个结论，
**是错的**。

真凶是**中文输入法**：`rt_probe` 用 `keybd_event` 打 ASCII，走的是

更坑的是击键会停在**未上屏的候选串**里 —— 界面上看得见候选预览，
但 `TextInput.text` 还是空，于是保存读到空串。

结果两者都拿到了值（`E按不出23 K按不出23`）—— 绑定是好的，是**值本身被改了**。

修法：`tools/rt_probe.py::typetext` 改为**一律走 `KEYEVENTF_UNICODE`**，不经输入法。
ASCII 也走这条路，别退回 `keybd_event`。

### 17. 用真实模型输出重放验证 Rust 侧解析（2026-09-25）

**问题**：`96%` 那个数字是 Python 探针打真端点跑出来的，Rust 侧只验过「形状能解析」
和「槽位能落到检索范围」—— **从没拿真实模型输出跑过**。而本机没有 API Key，没法重跑。

**办法**：`doc/Jev实测报告-措辞修正后.md` 里每个用例都记了**原始输出**（概率 + 槽位）。
拿它当夹具，走 `parse_answers` → `Intent::from_answers` 重放一遍，
断言 Rust 得出与探针**相同**的结论：

```rust
// src/core/decision/jev.rs::tests::real_probe_output_reproduces_the_same_slots
let json = serde_json::json!({"answers": {
    "is_search": {"type": "noul", "noul": 0.60},
    "type": {"type": "choice", "choice": "document", "confidence": 1.00},
    // …
}}).to_string();
let it = Intent::from_answers(&parse_answers(&json)?, "jev");
assert_eq!(it.is_search, true);   // 探针看到的也是 true
```

**这条测试是有牙齿的**：真实输出里全是贴着阈值的边界值 ——
`is_search` = 0.60 / 0.59 / 0.38，`is_natural` = 0.46。
`PASS_THRESHOLD = 0.5` 因此被夹在 **(0.46, 0.59]** 之间：改成 0.4 或 0.6 都会红。
阈值与探针不一致的话，界面上表现为「智能模式偶尔不解析」，极难定位。

**期望值取报告的「实际」列，不是「期望」列** —— 这里钉的是
「同一份输出 → 同一个结论」，而不是「模型答得对不对」（那是探针的活）。
`kw1` 那个已知错例（模型只给 0.38、被判成「不是搜索」）照样按 `0.38 → false` 钉住，
让已知限制是被**记录**的，而不是某天突然冒出来。

拼夹具用 `serde_json::json!` 而不是手写 `format!` 模板：手写 JSON 里的花括号要一个个
转义成 `{{`，错一个就是「测试自己把响应写坏了」，那种失败会伪装成产品缺陷。

**结果**：12 个用例、26 个槽位判定、置信度（三个槽位取最小值）**逐项一致**，

#### 三级闸门的实现要点

```rust
// 闸门 1：同步、< 1ms，可在 UI 线程直接调
pub fn analyze(&self, query: &str, settings: &AppSettings) -> Analysis
// 闸门 2/3：阻塞（云端硬超时 2000ms），必须在后台线程调
pub fn upgrade(&self, query: &str, settings: &AppSettings) -> Result<Option<Intent>>
```

**升级判据用的是「规则是否解析出槽位」，不是置信度阈值。**
规则已经认出来的查询没必要再花钱问模型；真正该云端出场的是
「我前几天弄的那个东西」这类**词表覆盖不到**的说法 —— 规则一个槽位都解析不出来，
而云端能听懂「前几天」。这比拍一个阈值更贴近实际意图。

`Intent::confidence` 只统计**真的解析出槽位**的那些问题：
未命中的槽位会回落到 `all` / `any`，把它算进来会让「什么都没解析出来」也显示成
0.30 而不是 0。实测：`docker` → **0.00**、`找一下昨天改的 docker 配置` → **0.85**。

**为什么 Jev 用 WinHTTP 而不是 reqwest/ureq**：
① 零新增依赖（项目已有 `windows` crate，只多开一个 feature），
引 rustls/native-tls 会让二进制和编译时间都明显变大；
② `WINHTTP_ACCESS_TYPE_DEFAULT_PROXY` 读的就是系统代理设置，
Clash Verge 开「系统代理」时自动生效，用户不必再配一遍。
需要显式代理时走 `WINHTTP_ACCESS_TYPE_NAMED_PROXY`（配置项 `ai_jev_proxy`）。

#### 实测：规则后端在真实查询上的表现

`anycast.exe --decide "查询"`（新增的命令行验证入口，见 §8）：

| 查询 | 语言 | 词数 | 值得调模型 | 类型 | 时间 | 置信度 | 耗时 |
| :--- | :--- | :-: | :-: | :--- | :--- | :-: | :-: |
| `docker` | 拉丁 | 1 | ❌ | 全部 | 不限 | 0.00 | 74 µs |
| `storage.rs` | 拉丁 | 1 | ❌ | 代码 | 不限 | 0.85 | 52 µs |
| 找一下昨天改的 docker 配置 | 混合 | 4 | ✅ | 代码 | 昨天 | 0.85 | 44 µs |
| 我前几天弄的那个东西 | CJK | 5 | ✅ | 全部 | 不限 | 0.00 | 55 µs |
| 今天天气怎么样 | CJK | 3 | ✅ | 全部 | 今天 | 0.85 | 59 µs |

闸门 1 的耗时稳定在 **50~75 µs**，远低于 1 ms 的预算。

> 注：「今天天气怎么样」的 `is_search` 判为**否**（命中闲聊词表「天气」），
> 所以虽然 `time=today` 解析成功，它不会被当成文件搜索 —— 这正是要防的假阳性。

**三个在实现中发现并修掉的坑**（都已补回归测试）：

1. **短词子串误命中**：`doc` 会命中 `docker`，导致纯关键词被当成「含类型词」
   送去调模型，**闸门 1 直接失效**。同理 `rs` 会命中 `hours`。
   → 英文词表一律改**词边界匹配**（允许单个 `s` 后缀以覆盖 `files`/`docs`）。
2. **中文词数恒为 1**：`split_whitespace` 对中文没有意义，
   于是「我前几天弄的那个东西」被当成单个孤立词、永远判不出自然语言。
   → 按 CJK 字符数折算词数（平均词长 2 字）。
3. **`WinHttpSendRequest` 报 `E_INVALIDARG`**：headers 是按**长度**传的 slice，
   不是以 `\0` 结尾的 C 字符串，多带一个 `\0` 就报 0x80070057。

### 18. 唤醒热键真机验证（2026-09-25，冲突 G 结项）

探针 `tools/hotkey_probe.py`。**结论：链路端到端可用（已证），
默认值 `Alt+Space` 也已由物理按键确认可用（§18.4）。**

#### 18.1 链路

```
RegisterHotKey(Alt+Space, MOD_ALT|MOD_NOREPEAT)
   → WM_HOTKEY(id=WAKE_HOTKEY_ID)
   → SysEvent::WakeHotkey → BackendNotification::WakeRequested
   → gui::toggle_window() → show_window() / hide_window()
```

注册落在隐藏的消息窗口 `AnycastSystemBusWindow`（`HWND_MESSAGE` 子窗口）上，
**与主窗口是两个不同的 HWND**。注意它枚举不到 —— `EnumWindows` 不列 message-only 窗口，
得用 `FindWindowExW(HWND_MESSAGE, ...)`。

#### 18.2 两条互补证据

**① 注册归属（客观，不依赖窗口状态）**

从探针进程去 `RegisterHotKey` 同一个组合键。被占用则返回
`ERROR_HOTKEY_ALREADY_REGISTERED = 1409`。

| 组合键 | err | 判读 |
| :--- | :--- | :--- |
| `Alt+Space`（应用在跑） | **1409** | 应用确实占住了 |
| `Alt+Space`（应用没跑，基线） | 0 | 谁都能抢 → 1409 是应用造成的 |
| `Ctrl+Alt+Shift+F13`（对照） | 0 | 判据本身有效 |

**对照不能省**：没有它，1409 也可能来自别的程序或沙箱拦截，
而「抢到了」也可能只是判据失灵。

**② 投递效果（行为，两个方向都测）**

| 方向 | 起始状态 | 按热键后 | 结果 |
| :--- | :--- | :--- | :--- |
| A 隐藏 | visible + 前台 | **visible=False** | ✅ 热键真的到了 |
| B 唤出 | **隐藏**（= 关窗后的托盘态） | **visible=True + 前台** | ✅ **核心命题成立** |

方向 B 才是用户实际走的那条路（关掉窗口 = 隐藏到托盘，此后只能靠热键或托盘图标唤回）。
方向 A 不能省：窗口本来就可见时，`show_window()` 走完也不改 `visible`，
判据分不出「热键没触发」和「触发了只是重复显示」；隐藏方向没有这个歧义。

**实测用的是 `Ctrl+Shift+Space`（把配置临时改掉），原因见 18.3。**

#### 18.3 `Alt+Space` 无法用合成按键验证（本节的真正收获）

第一轮拿默认值 `Alt+Space` 跑，注册 1409 成功、**但按键投递毫无反应**。
在断定是产品缺陷之前先做了三层排除，结果全部指向「不是应用的问题」：

**第一层 · 注入有效性自检** —— 探针自己注册一个热键、注入它、看自己收不收得到
`WM_HOTKEY`。没有这一步，「发了键没反应」永远有两种解释。自检通过（`Ctrl+Shift+F13`）。

**第二层 · 可测性矩阵** —— 逐个试哪些组合注入得动：

| 注入**能**触发 | 注入**触发不了** |
| :--- | :--- |
| `Alt+Esc` · `Alt+Enter` · `Alt+P` · `Alt+Z` · `Alt+0` | `Alt+Space` |
| `Ctrl+Space` · `Ctrl+Shift+Space` · `Ctrl+Alt+Shift+Space` | `Ctrl+Alt+Space` |
| `Ctrl+Alt+P` · `Ctrl+Alt+F13` · `Ctrl+Shift+F13` | `Alt+Left` |

规律：**`Alt`+`Space` 不带 `Shift` 就必败**。加上 `Shift` 立刻恢复
（`Ctrl+Alt+Shift+Space` ✅）—— 这正是**系统菜单加速键**（`Alt+Space` = 打开系统菜单）
的特征。`Alt+Esc` / `Alt+Enter` 能过，说明不是 Alt 本身的问题。

**第三层 · 消息级诊断** —— 注册 `Alt+Space` 后注入，把收到的所有消息打出来：

```
WM_SYSKEYDOWN  vk=0x12   ← Alt 按下
WM_SYSKEYUP    vk=0x20   ← Space 抬起（**但没有 Space 按下**）
WM_KEYUP       vk=0x12   ← Alt 抬起
```

**Space 的按下事件凭空消失**，而对照的 `Ctrl+Shift+F13` 正常收到 `WM_HOTKEY`。
`Space 按下` 从未进入消息队列 → 吞键发生在**投递之前**，即系统层。

**排除掉的变量**（每项都实测）：

| 变量 | 排除方式 | 结果 |
| :--- | :--- | :--- |
| 注入 API | `keybd_event` vs `SendInput`（带扫描码） | 两者完全一致 |
| 注入时序 | 组合压进**一次** `SendInput`（零间隔） | 仍是 ❌（但让 `Ctrl+Alt+Space`、`Alt+Tab` 从 ❌ 变 ✅，见下） |
| `MOD_NOREPEAT` | 注册时带 / 不带 | 两者都 ❌ |
| 目标窗口的系统菜单 | `WS_OVERLAPPEDWINDOW` vs `WS_POPUP` | 完全一致 → 不是目标窗口的菜单 |
| 键盘布局 / 输入法 | 本机只装 `HKL=0x08040804`（简中）；激活 en-US 后重试 | 仍是 ❌ |

**顺带发现（有独立价值）**：零间隔注入把 `Ctrl+Alt+Space`、`Alt+Tab` 从 ❌ 变成 ✅。
说明 `keybd_event` 版本在修饰键与主键之间那 20ms 间隔，会让系统先进入「菜单模式」，
随后的键被当菜单激活键吞掉。**做注入测试时，组合键要一次发完，不要逐个 sleep。**
这条一度让人以为「`Ctrl+Alt+Space` 也不可用」，是探针的时序伪影。

#### 18.4 `Alt+Space` 已由物理按键确认可用（冲突 G 结项）

探针能查到的最深处就是 18.3。**「合成按键触发不了」推不出「真实按键触发不了」**，
所以没有把它当缺陷报。**2026-09-25 用户物理按键实测：窗口正常弹出。**

→ **默认值 `Alt+Space` 保留。** 18.3 的现象是**合成输入的伪影**，不是产品缺陷。

这一步值得单独记下来的原因是它的**方法论**：如果当时只看「注册 1409 成功但按键没反应」
就下结论，会得到一个完全错误的产品判断 —— 要么白改默认值，要么去修一个根本不存在的 bug。
**代价是三层排除 + 逐项排除 5 个变量；收益是不冤枉代码。**

如果将来要复现「真实按键」的场景，只有两条路：物理按键，或者用户手动验证。
脚本这条路上，`Alt+Space` 家族（`Alt`+`Space` 不带 `Shift`）是**不可注入**的，
验证时请改用 `Ctrl+Shift+Space` 之类的等价组合键。

#### 18.5 探针自己踩的坑（都会骗人）

- **类名必须唯一**：`RegisterClassW` 用固定类名时，第二次返回
  `ERROR_CLASS_ALREADY_EXISTS(1410)`，被「跳过」分支吃掉 → 表现为
  **一个进程里只有第一次的结果是真的，后面全是假 ❌**。差点据此得出
  「`Alt+Space` 注入不了」的错误结论
- **`CreateWindowExW` 必须给 `argtypes`**：否则 `HWND_MESSAGE(-3)` 被零扩展成
  `0x00000000FFFFFFFD`，返回 `1400`（无效句柄）
- **`send_combo` 要认单字母键**：`VK` 表里没有字母，遇到 `Alt+P` 直接 `SystemExit`，
  把整个矩阵测试打断在半路（看起来像「跑到一半崩了」）
- **`keys()` 不能用来测热键**：`rt_probe.keys()` 第一步就 `force_foreground()`，
  自己会把窗口 `ShowWindow` 出来 —— 拿它测「热键能不能唤出窗口」等于
  先把结论做出来再验证，必然假阳性。本探针一律不碰前台状态
- **「抢不到」≠「注入不了」**：应用占着目标组合键时自检会拿 1409。
  把它报成「注入不了」方向正好反了 —— 那其实是**注册成功**的证据


### 19. 快捷直达真机验证（2026-09-25，Phase 0 第 1 项收尾）

探针 `tools/hotkey_probe.py bindings`。**结论：注册归属、触发效果、两个守卫全部符合预期。**

#### 19.1 链路

```
storage.hotkeys (SQLite)
  → reload_hotkeys() → HotkeyBindingModel 列表
  → sync_bindings()  → bus.set_bindings([(BINDING_ID_BASE + i, spec)])
  → RegisterHotKey
  → WM_HOTKEY(id >= BINDING_ID_BASE)
  → SysEvent::BindingHotkey(id) → idx = id - BINDING_ID_BASE
  → hotkeys[idx] → enabled? → launcher::activate_or_launch(target, item_type)
```

#### 19.2 用「标记文件」当信号

绑定项的效果是「启动某个目标」，用「某个窗口冒出来了」当判据太软
（窗口可能本来就在）。改为让靶子写一个标记文件 —— **「文件出现」是确定性的、可轮询的，
而且能区分是哪一个绑定被触发**。

> 这一点不是洁癖：**索引错位那类 bug 只有靠「哪个靶子被写」才看得出来**。
> 三个绑定都指向同一个靶子的话，第 2 个和第 3 个触发起来长得一模一样。

#### 19.3 测例设计：中间那个禁用

| # | hotkey | enabled | 靶子 | 期望 |
| :-: | :--- | :-: | :--- | :--- |
| 1 | `Ctrl+Shift+F9` | ✅ | `marker_A` | 注册 + 触发 A |
| 2 | `Ctrl+Shift+F10` | ❌ | `marker_B` | **不注册** + 不触发 |
| 3 | `Ctrl+Shift+F11` | ✅ | `marker_C` | 注册 + 触发 **C** |

**第 2 项禁用是刻意的**。`sync_bindings` 里的下标来自
`.enumerate().filter(enabled).filter_map(parse)` —— 若谁把下标改成「过滤后的序号」，
第 3 项会被注册成 `BINDING_ID_BASE + 1`，按下后落到**被禁用的第 2 项**上，
早退、无标记。**这个测例能把这个错误抓出来。**

#### 19.4 实测结果

| 项 | 期望 | 实测 |
| :--- | :--- | :--- |
| `Ctrl+Shift+F9` 注册 | 已注册 | `err=1409` ✅ |
| `Ctrl+Shift+F10` 注册 | **未注册** | `err=0` ✅ |
| `Ctrl+Shift+F11` 注册 | 已注册 | `err=1409` ✅ |
| `Ctrl+Shift+F9` 触发 | 出现 marker_A | 出现，内容 `'A'` ✅ |
| `Ctrl+Shift+F11` 触发 | 出现 marker_C | 出现，内容 `'C'` ✅ |
| 总开关关 → 注册 | 全部未注册 | 两个都 `err=0` ✅ |
| 总开关关 → 触发 | 全部不出现 | 都不出现 ✅ |

**索引对齐正确**（第 3 项打中的是 C 而不是被禁用的 B）。
两个守卫都验了：`enabled` 单项守卫（19.3 第 2 项）与 `hotkeys_master_enabled` 总开关。

#### 19.5 探针又骗了一次（同一类错误，第二次）

跑 `Ctrl+Shift+F9/F10/F11` 的可注入性预检，三个全报 ❌「注入不动」，
而 `Ctrl+Shift+F13` ✅。分界过于整齐，去查才发现：

**`VK` 表里只有 `f13`/`f14`，`spec_of("Ctrl+Shift+F9")` 返回 `vk=None`**，
自检于是走「解析不了 → 跳过」分支返回 `None`，被上层读成「注入不动」。
**键根本没被发出去。**

修法：抽出统一的 `vk_of(name)`，支持 `F1`~`F24`（`0x70 + n - 1`，与应用
`hotkey::vk_of_key` 一致）+ 单字母数字 + 符号键，**所有发送函数共用它**。
修完四个组合键全部 ✅。

> 这与 18.5 的「假 ❌」是**同一类错误**：探针把「我不认识这个输入」报成了
> 「被测对象有问题」。**探针的每一种失败都必须能区分「环境不行」和「被测不行」。**
