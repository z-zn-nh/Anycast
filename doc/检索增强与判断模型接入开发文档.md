## 2. 判断模型事实层

### 2.1 Jev（云端，闭源）

TypeSafe AI 出品（创始人 Diogo Almeida，前 OpenAI，InstructGPT / RLHF 论文共同作者），
2026-09-15 发布，官方称第一个公开的「System One」模型。

| 约束 | 数值 / 说明 |
| :--- | :--- |
| 输出 | `Choice`（选一个）/ `Score`（打分）/ `Noul`（0~1 概率），均带置信度 |
| 延迟 | 端到端 **70~500 ms** |
| 成本 | 输入 **$0.042 / M token**，输出免费 |
| 候选上限 | **255** |
| 输入 | 仅文本；**无状态**（不记忆历史） |
| 中文 | 官方标注 CJK「可用但准确率不等同英文」 |
| 可用性 | 节点集中在美国西海岸，**中国大陆无法直接使用** |
| 权重 | **闭源**，仅 API |
| 准确率 | **不高于大模型**：TypeSafe 自评 67.8% vs 基线 74.1%；Banking77 实测 81.0% vs Claude Opus 5 84.4% |

### 2.2 Laya（本地，开源）★ 本项目主选

| 项 | 内容 |
| :--- | :--- |
| 作者 | Convai Innovations（Nandakishor Mukkunnoth），2026-09-18 开源 |
| 许可 | **Apache 2.0**，权重可直接下载，可商用，**支持内网 / 气隙部署** |
| 仓库 | Hugging Face `convaiinnovations/laya`（公开、非 gated，实测 3452 likes） |
| 定位 | 非自回归 System 1 决策模型；**三种原语与 Jev 完全一致** |
| 实测体积 | 仓库总占用 **2,366,100,536 B ≈ 2.2 GB**（英文 ~808 MB / 多语言 ~647 MB） |

**三个 checkpoint**（同一仓库的不同子目录，按需下载）：

| 子目录 | 底座 | 参数 | 上下文 | 适用 |
| :--- | :--- | :--- | :--- | :--- |
| `laya`（根） | ModernBERT-large | 421 M | 512 | 英文分类、护栏、邮件分诊 |
| **`multilingual`** | **mmBERT-base** | **322 M** | 1024（编码器可到 8k） | **100+ 语言，本项目用这个** |
| `typed-decisions` | ModernBERT-large | 421 M | 1024 | 四类合成工作流微调版 |

**与 Jev 的对比**（口径：Laya 侧为官方自测，Jev 侧为第三方实测，**非同轮受控对测**）：

| 指标 | Jev 1.13.0 | Laya (routed) | 结论 |
| :--- | :--- | :--- | :--- |
| typed-decisions | 0.727 | **0.766** | Laya 微胜 |
| AG News（4 类） | 0.910 | **0.950** | Laya 微胜 |
| DAIR Emotion（6 类） | 0.480 | **0.595** | Laya 胜 |
| **Banking77（77 类）** | **0.870** | 0.425 | **Jev 大胜**（选项过多所致） |
| ECE（越低越好） | 0.246 | **0.081** | Laya 胜 |
| 单题 P50 延迟 | 236~276 ms | **32.8 ms**（T4） | Laya 约 7.8 倍 |
| 成本 | $0.042/M token | **$0**（自托管） | Laya |

### 2.3 官方承认的三个短板（本项目必须处理）

1. **零样本接近瞎猜**：基础 checkpoint 在 typed-decisions 零样本只有 **0.362**
   （随机基线 0.318、多数类 0.461）。那个 0.766 是**微调后**的成绩。
   → **不微调直接用，等于没用。**
2. **选项超过 20 个就崩**：所有选项共享固定 `head_max_len`（英文 192 / 多语言 256 token），
   77 个选项摊到每个只剩 3~4 token，Banking77 的 0.425 就是这么来的。
   → **选项必须控制在 20 以内**（本项目槽位设计远低于此，见 §5.3）。
3. **出厂过度自信**：英文版温度重拟合前 ECE 0.466；多语言版出厂压根没拟合。
   → **必须按（题型 × 选项数）重新拟合温度**，否则置信度门禁不可信。
   另：`score` 是最弱原语（SST-5 仅 0.372），算术 / 计数 / 日期比较**不要交给它**。

| :--- | --: | --: | --: | :--- |

| moderation and safety | 2708 | 0.967 | 0.061 | — |
| topic classification | 749 | 0.939 | 0.029 | — |
| emotion and tone | 1825 | 0.906 | 0.018 | — |
| inference and fact checking | 3022 | 0.883 | 0.054 | — |
| instruction-following | 600 | 0.878 | 0.046 | — |
| reading comprehension | 770 | 0.847 | 0.083 | — |
| **search relevance** | 733 | **0.628** | 0.066 | ⚠️ **重排相关，只有 0.628** |
| **response quality scoring** | 3146 | **0.581** | 0.023 | ⚠️ **score 原语偏弱** |
| conversation outcomes | 3600 | 0.482 | 0.019 | — |
| **sentiment and rating** | 961 | **0.442** | **0.438** | ⚠️ 最弱，且校准极差 |

整体：accuracy 0.753、ECE 0.030、50% 覆盖率时准确率 0.947。
零样本（held-out 任务族）：整体 0.651、ECE 0.204。

延迟（官方）：1 题 p50 **38.4 ms** / 10 题 p50 156 ms / 50 题 p50 721 ms。

> ### ⚠️ 由此得出的定位修正（重要）
>
> 原方案把「结果重排」也交给判断模型。**数据不支持这个做法**：
> `search relevance` 仅 **0.628**、`response quality scoring` 仅 **0.581**，
> 都明显弱于 `intent and routing` 的 **0.991**。
>
> **修正后的职责划分**：
>
> | 职责 | 由谁承担 | 依据 |
> | :--- | :--- | :--- |
> | 意图解析（类型 / 时间 / 位置槽位） | ✅ **Laya** | intent and routing 0.991 |
> | 查询路由（极速 / 智能） | ✅ **Laya** | 同上 |
> | **结果重排打分** | ❌ **本地排序算法** | search relevance 仅 0.628 |
> | 算术 / 计数 / 日期比较 | ❌ **确定性代码** | score 原语最弱 |
>
> 即：**Laya 只负责「听懂」，不负责「排名」。**
> 这让它的职责更窄、更可靠，也正好避开它最弱的两项能力。

### 2.4 本项目实测证据（自取配置，非转述）

**`multilingual/rl_agent_config.json`**
```json
{
  "encoder": "jhu-clsp/mmBERT-base",
  "head_layers": 2,
  "max_len": 1024,
  "head_max_len": 256,
  "max_prefixes": 6,
  "amp_dtype": "bf16",
  "temperature": [1.0, 1.0, 1.0],
  "temperature_by_options": {},
  "training": { "updates": 15987, "epochs_completed": 4, "hours": 4.97, "world_size": 1 }
}
```
> **确认**：`temperature` 全为 1.0、`temperature_by_options` 为空
> → **多语言版出厂未做温度校准**，与 §2.3 第 3 条一致。
> **这是本项目接入前必须补的第一件事。**

**`multilingual/encoder/config.json`（关键字段）**
```json
{
  "architectures": ["ModernBertForMaskedLM"],
  "model_type": "modernbert",
  "num_hidden_layers": 22,
  "num_attention_heads": 12,
  "hidden_size": 768,
  "intermediate_size": 1152,
  "vocab_size": 256000,
  "position_embedding_type": "sans_pos",
  "rope_parameters": {
    "full_attention":     { "rope_theta": 160000 },
    "sliding_attention":  { "rope_theta": 160000 }
  },
  "tie_word_embeddings": true
}
```
> **重要**：`position_embedding_type = "sans_pos"` —— 用 **RoPE** 而非可学习位置嵌入表，
> 因此**序列长度是动态的**，ONNX 导出对动态轴非常友好（无需固定 max_len 的 embedding 表）。

**`multilingual/tokenizer/tokenizer_config.json`（关键字段）**
```json
{ "tokenizer_class": "PreTrainedTokenizerFast", "model_max_length": 8192, "padding_side": "right" }
```
> **重要**：是 **fast tokenizer**，`tokenizer.json`（实测 34,363,188 B ≈ 34.4 MB）
> **可被 Rust `tokenizers` crate 直接加载**，运行时无需 Python。

**仓库文件清单结论**：**无 ONNX 文件**；决策头逻辑在 Python 代码里
（`rl_agent_api.py` / `rl_common.py`）。**Rust 落地需自备一次性导出脚本。**

### 2.5 决策模型结构（读 `rl_common.py` 得出）

```
h = encoder(input_ids, attention_mask).last_hidden_state   # ModernBERT 22 层，768 维
h = h + type_emb(qtype)                                     # nn.Embedding(3, 768)  ← 一行查表
h = head(h, src_key_padding_mask=pad)                       # 2 层 TransformerEncoderLayer（全序列自注意力）
m = gather(h, marker_pos)                                   # 每个选项取自己的 [MASK] 标记位
logits = scorer(m)                                          # LayerNorm → Linear(768,768) → GELU → Linear(768,1)
logits = masked_fill(~marker_mask, -1e4)
# act_head（"直接作答 vs 升级"）：pooled + [top1, top1-top2, 熵, k/255]
#                                 → Linear(772,256) → GELU → Linear(256,2)
```

序列构造（`build_sequence`）：

```
[CLS] "<type> question: <instructions>" [SEP] [MASK]opt0 [MASK]opt1 … [SEP] <state> [SEP]
                                                ↑ markers 记录每个 [MASK] 的位置
```

### 2.6 Rust 落地可行性评估

| 组件 | 能否 Rust 化 | 说明 |
| :--- | :--- | :--- |
| 分词器 | ✅ 直接可用 | `tokenizer.json` 是 fast tokenizer，Rust `tokenizers` crate 原生支持 |
| 编码器（ModernBERT 22 层） | ✅ ONNX 可导出 | RoPE + 无位置表 → 动态轴友好；标准算子 |
| `type_emb` | ✅ 易 | 3×768 查表 |
| `head`（2 层 TransformerEncoder） | ✅ ONNX 可导出 | 标准 `TransformerEncoderLayer` 算子 |
| `scorer` / `act_head` | ✅ 易 | LayerNorm / Linear / GELU |
| `render_options` + `build_sequence` | ⚠️ **需逐 token 对齐移植** | 纯字符串 + 分词逻辑，约 60 行 Rust，但**必须与 Python 完全一致**，否则 marker 位置错位 |
| 温度缩放 + softmax + 三原语解码 | ✅ 易 | 约 40 行 |
| 依赖 | ONNX Runtime（`ort` crate） | 二进制体积约 +10~20 MB |

> **结论：路径清晰，无阻塞，属中等工作量。** 唯一必须自备的是**一次性 ONNX 导出脚本**
> （Python 侧跑一次，产出 `.onnx` 并保留 `tokenizer.json`），之后运行时**完全不需要 Python**。

### 2.7 选型结论

**选 Laya（本地），Jev 降为可选预留。** 理由：

1. **满足「尽量不走云端」** —— 这是唯一符合的选项；
2. **让 Local-first 原则得以保留**（设计文档 §2.1 无需打破，只需补充边界）；
3. **消解两个硬约束**：不再需要代理、不再受「中文弱于英文」困扰（多语言版覆盖 100+ 语言）；
4. **选项 ≤20 甜点区** —— 本项目槽位枚举（类型 8 / 时间 8 / 位置 4）**正好落在甜点区**，
   恰好避开 Laya 最弱的「选项过多」场景；
5. 三原语与 Jev 一致 → **抽象层可共用**，日后切换云端只需换实现。

**代价（必须接受）**：

- ① 需自备 ONNX 导出 + Rust 移植（中等工作量）；
- ② **必须微调 + 温度校准**（零样本 0.362 ≈ 瞎猜），这是最大隐性成本；
- ③ 多语言权重约 650 MB，**必须懒加载**，否则违反 §27「Idle RAM 尽量低」；
- ④ CPU 单次 193~464 ms，**必须异步、不阻塞首屏**。

## 4. 检索质量提升：不依赖判断模型的那一半（P0）

> **这一节才是本轮「效果提升」的真正来源。** 判断模型不提升准确率。

### 4.1 现状

| 项 | 现状 |
| :--- | :--- |
| 索引 | `walkdir` 全量 + `notify` 增量 → SQLite（约 4.8 万条 / 10.4 s） |
| 搜索 | SQLite 直查 + 内存打分，实测 `docker` 约 5 ms |
| 缺失 | 无 FTS5、无中文分词、无内容索引、无 USN Journal |

### 4.2 提升项（按性价比排序）

| 优先级 | 措施 | 预期收益 | 备注 |
| :-: | :--- | :--- | :--- |
| **P0** | SQLite **FTS5** 全文索引（文件名 + 路径 + 内容） | 子串 / 词级检索从 O(n) 全表扫降到索引查找 | 见下方警告 |
| **P0** | **中文分词**：FTS5 `trigram` tokenizer，或 jieba-rs 预分词后入库 | 中文查询不再依赖 `LIKE '%…%'` | 建议先试 trigram |
| **P0** | **排序模型**：前缀命中 > 词首命中 > 中间命中；叠加使用频率 / 最近使用 / 类型权重 | 「检索效果更好」的直接来源 | 纯本地，零成本 |
| **P1** | 拼音首字母（项目已有 `pinyin` 依赖） | 输入 `vs` 命中 Visual Studio | 依赖已存在 |
| **P1** | **USN Journal** 增量替代 walkdir 全量 | 索引从 10 s 降到近实时 | 需 Win32 |
| **P2** | `sqlite-vec` + 本地 `bge-small-zh` | 语义相似检索（**不依赖网络**） | 模型体积待评估 |

> **会触发 SQLite 重新编译** —— 在提交量受限的机器上请预留时间（见 `.cargo/config.toml`）。

## 5. 判断模型接入设计（Laya 为主）

### 5.1 定位：只做两件事（已按 §2.3.1 修正）

```
用户输入
   │
   ├─ ① 意图解析（Choice / Noul）→ 槽位：类型 / 时间 / 位置
   └─ ② 查询路由（Choice）→ 极速 / 智能 / 混合
```

**明确不做**：

- ❌ 不生成关键词（避免幻觉，关键词必须由本地分词产出）
- ❌ 不生成文本、不回答开放问题
- ❌ **不做结果重排打分** —— 官方 `search relevance` 仅 **0.628**、`response quality scoring` 仅 **0.581**，
  明显弱于 `intent and routing` 的 **0.991**。**重排交给本地排序算法**（前缀 > 词首 > 中间 + 频率/时间/类型权重）
- ❌ 不做算术 / 计数 / 日期比较（用确定性代码）

### 5.2 触发策略（省电 + 保速度）

| 输入形态 | 是否触发 | 说明 |
| :--- | :--- | :--- |
| 纯关键词（`docker`、`vs`） | ❌ 永不 | 本地检索直接出结果 |
| 自然语言（含动词 / 时间词 / 疑问词） | ✅ 异步触发 | 「找一下昨天改的 EasyNote 文档」 |
| 用户手动切到「✦ 智能搜索」 | ✅ | 显式意图 |

判定用**本地规则**（正则 + 词表），零成本、零延迟。

### 5.3 意图解析的槽位设计（必须落在 20 选项以内）

| 维度 | 候选选项 | 数量 |
| :--- | :--- | :-: |
| 类型 | 全部 / 文档 / 代码 / 图片 / 音视频 / 压缩包 / 可执行 / 文件夹 | 8 |
| 时间 | 今天 / 昨天 / 本周 / 上周 / 本月 / 今年 / 更早 / 不限 | 8 |
| 位置 | 不限 / 当前目录 / 指定盘符 / 常用目录 | 4 |

> **三个维度分别调用，各自远低于 20** —— 正好落在 Laya 的甜点区。
> 若合并成单次调用会超出上限并显著掉准，**不要合并**。

> **关键设计：关键词不由判断模型生成。**
> 判断模型只做 Choice / Noul，不产出自由文本 —— 这正是它杜绝幻觉的机制。
> 因此**关键词提取必须留在本地**（分词 + 拼音 + 倒排召回），
> 判断模型只负责把「昨天」「文档」这类**语义槽位**映射到预设枚举。

**示例**：输入「找一下我昨天修改的 EasyNote 文档」

```
本地：分词 → 关键词 = [EasyNote]（用于召回）
判断：Choice(类型) = 文档 · Choice(时间) = 昨天 · Noul(要求含 EasyNote) = 0.94
→ 本地按槽位过滤 → 本地排序算法排名（非判断模型）→ 输出
```

### 5.6 双后端架构（可切换）

需求：**「不妨做两版出来，或者提供给用户选择」**。设计为可插拔后端：

```rust
// src/core/decision/mod.rs
pub trait DecisionBackend: Send + Sync {
    fn id(&self) -> &'static str;          // "rule" | "laya" | "jev"
    fn display_name(&self) -> &'static str;
    fn is_local(&self) -> bool;
    fn is_available(&self) -> bool;        // 权重存在 / API Key 已配置
    fn warm(&self) -> Result<()>;          // 预加载（仅本地模型需要）
    fn decide(&self, state: &str, questions: &[Question]) -> Result<Answers>;
}
```

| id | 实现 | 依赖 | 延迟 | 成本 | 默认 |
| :--- | :--- | :--- | :--- | :--- | :-: |
| `rule` | 纯规则（正则 + 词表 + 日期解析） | 无 | < 1 ms | 0 | ✅ 开 |
| `laya` | 本地 ONNX（`tokenizers` + `ort`） | 约 650 MB 权重 | 200~460 ms | 0 | 关 |
| `jev` | 云端 HTTP | API Key + 代理 | 70~500 ms | $0.042/M | 关 |

设置项（写入设计文档 §25）：

```
AI 后端策略
├── Backend Mode (自动 / 仅规则 / 本地模型 / 云端模型)
├── Local Checkpoint (英文根版 421M / 多语言版 322M / 按查询语言自动)
└── Cloud Fallback (本地低置信时是否升级到云端，默认关)
```

「**自动**」的语义：`rule` → `laya` →（若开启）`jev`，逐级升级，任一级成功即止。

### 5.7 智能调用：三级闸门

需求：**「智能化调用，必要时才使用模型」**。实现为三道闸门：

```
输入
 │
 ├─ 闸门 1 · 本地规则（<1ms，零成本）
 │    纯关键词 / 前缀指令 / 已知模式 → 直接检索，【不调模型】
 │
 ├─ 闸门 2 · 本地模型 Laya（200~460ms，零成本）
 │    规则判定为自然语言 → 【先出本地结果】→ 异步解析槽位 → 二次检索
 │
 └─ 闸门 3 · 云端模型 Jev（70~500ms，低成本）
      仅当「用户显式开启」且「本地置信度 < 阈值」时触发
      【超时 800 ms 直接放弃，不阻塞】
```

三条硬性规则：

1. **首屏永远由本地检索提供**。模型结果只做**增量替换**，不得清空已渲染列表；
2. **任何一级失败或超时 → 静默降级到上一级**，不弹错误提示；
3. **纯关键词输入永不触发闸门 2 / 3**（由闸门 1 的本地规则判定）。

### 5.8 语言策略（回应「搜索大部分文件都是英文」）

> ⚠️ **关键区分：目标文件名的语言 ≠ 用户查询的语言。**

「搜索大部分文件是英文」指的是**目标文件名**（`Dockerfile`、`main.rs`、`docker-compose.yml`）。
但**用户敲进搜索框的查询**完全可能是中文：

| 用户输入（查询） | 命中目标（文件名） | 语言关系 |
| :--- | :--- | :--- |
| 「找一下昨天改的 docker 配置」 | `docker-compose.yml` | **中文查询 → 英文文件** |
| 「那个写存储逻辑的文档」 | `storage.rs` / `architecture.md` | **中文查询 → 英文文件** |
| `docker compose` | `docker-compose.yml` | 英文 → 英文 |

前两行是**跨语言检索**，正是多语言版的价值所在。
**这件事必须实测，不能凭「文件是英文的」推断「查询是英文的」。**

**checkpoint 选择策略**：

| 场景 | 建议 checkpoint | 体积 | 说明 |
| :--- | :--- | :--- | :--- |
| 查询以**英文**为主 | `laya` 英文根版 | 808 MB | 英文任务更准，且无需中文分词 |
| 查询含**中文** | `laya-multilingual` | 647 MB | 覆盖 100+ 语言 |
| 不确定 | **先埋点** | — | 记录真实查询的语言分布再决定 |

> **两个 checkpoint 不要同时加载**（合计约 1.45 GB，违反 §27 内存约束）。
> 官方 `Router` 是「按需切换」，但切换冷启动 7~10 s。
> 本项目改为**用户显式选定一个**，设置页给出上表作为选择依据。

**落地建议（三步走）**：

1. **第一步只做规则版 + 埋点** —— 零成本先跑起来，记录查询语言分布；
2. 拿到分布后再决定装英文版还是多语言版；
3. 若分布混合 → 优先多语言版（英文能力虽略逊英文根版，但覆盖更全）。

### 5.9 关于「若不考虑本地优先，Jev 是否更合适」

诚实评估：**Jev 的优势场景与本项目并不完全吻合。**

| Jev 的优势 | 本项目是否需要 |
| :--- | :--- |
| Banking77 77 类 0.870（宽标签空间） | ❌ **不需要** —— 本项目槽位只有 8 个，用不上多类优势 |
| 零配置、无需微调 | ✅ **需要**（这是 Jev 的真优势） |
| 无需下载权重 | ✅ 需要 |
| 英文强 | ⚠️ 取决于实测（见 §5.8） |
| **中文弱（CJK）** | ❌ **硬伤**（若查询含中文） |
| 需代理 + 网络不确定性 | ❌ 与「快速启动」目标冲突 |

**结论**：Jev 真正的价值是**省掉微调与权重管理**，而不是更准
（§2.1 已述：其准确率并不高于大模型）。

- 若实测确认「查询以英文为主 + 不愿投入微调」→ **Jev 是合理选择**；
- 但只要查询含中文，它的 CJK 短板会直接伤到体验。

**所以双后端是对的**：把选择权留给用户，并用**实测数据**而非猜测来决定默认值。
